# 008：番剧封面加载优先级与响应式图片优化

## 问题摘要

普通番剧列表把前 10 个卡片都标记为 `priority`，随后统一映射为 `loading="eager"` 和 `fetchPriority="high"`。页面网格在不同视口下每行只有 2–7 张，前 10 张不一定都处于首屏，也不应全部竞争最高网络优先级。

封面 URL 选择逻辑倾向 v0 API 的 `medium`（约 `/r/800/`）或日历接口的 `large`，但最终 `<img>` 只有单一 `src`，没有 `srcset`/`sizes`。因此小卡片可能下载远大于其显示需求的图片。外部 Bangumi 图源是否支持稳定、可缓存的尺寸变体，必须先验证；不能在计划中假定任意改 URL 即有效。

## 当前证据

### 已静态确认

1. `start/app/routes/anime/layout.tsx:190-199` 渲染列表卡片，并对 `idx < 10` 的前 10 项传入 `priority`。
2. `start/app/components/anime-card.tsx:30-35` 将 `priority` 原样传给 `AnimeCover`。
3. `start/app/components/anime-cover.tsx:50-64` 只渲染一个 `src`；`priority=true` 时使用 `loading="eager"` 与 `fetchPriority="high"`，否则使用 `lazy` 与 `low`。
4. `start/app/lib/anime-meta.ts:19-46` 优先选择含 `/r/800/` 的 v0 `medium`，日历数据则优先 `large`，最后回退到其他单一 URL。
5. `start/app/components/anime-card.tsx:30-36` 的卡片封面容器为 `aspect-[2/3]`，但没有向浏览器提供响应式图片候选。

### 需要运行时验证

- 各断点首屏实际可见封面数量；导航、筛选区和视口高度都会影响结论。
- 高优先级请求是否挤占 CSS、字体、路由数据或真正的 LCP 图片。
- 各 URL 的真实像素尺寸、传输字节、缓存头、跨域响应和稳定性。
- Bangumi 图片服务是否有正式、可依赖的尺寸转换规则；当前仅能从 URL 形态和注释看出来源差异。
- 浏览器实际选择的 LCP 元素及封面解码对主线程的影响。

## 工作原理 / 为什么会慢

`loading="eager"` 会让浏览器立即考虑加载图片，`fetchPriority="high"` 又提示网络调度器提高优先级。优先级只是提示，但同时给 10 张图高优先级会稀释“最关键资源”的信号。在带宽和连接数受限时，这些请求可能互相竞争，也可能排在更关键的 CSS、字体或首张可见封面之前。

响应式图片的关键不是 CSS 把大图缩小，而是让浏览器在请求前就知道“这个位置大约需要多宽”。当前只有 `src`，浏览器无法选择更小候选。`/r/800/` 或 `large` 可能适合较大显示，但普通列表卡片在手机两列、桌面多列时通常不需要同样大的源图；具体浪费量需要读取响应元数据后计算。

外部图片还涉及来源可靠性、限流、缓存和防盗链。若建立同源图片代理，代理可以规范尺寸与格式，但必须限制允许域名、尺寸和输出格式，否则会变成开放代理并放大成本与安全风险。

## 影响

- **网络竞争**：10 个高优先级图片可能使关键请求调度失真。
- **传输字节**：单一大尺寸源可能导致移动端过度下载。
- **LCP**：首张关键封面可能受益于高优先级，也可能被其余 9 张竞争；方向需实测。
- **外部依赖**：第三方图源速度和失败率直接影响列表体验。
- **数据成本**：移动网络用户承担不必要的图片流量。

## 优化目标

1. 默认只有最可能位于首屏且可能影响 LCP 的前 1–2 张封面使用高优先级；最终数量由实测决定。
2. 其余封面使用浏览器原生懒加载和正常/低优先级，不在首屏同时争抢网络。
3. 为列表封面提供与布局匹配的响应式候选和准确 `sizes`。
4. 若引入代理，保证域名白名单、尺寸上限、格式协商、缓存和失败回退完整。
5. 保持封面占位比例稳定，避免 CLS，且不降低日历大卡片的清晰度。

## 非目标

- 不改变番剧排序、分页、卡片布局或封面来源的业务规则。
- 不在当前计划阶段实现图片代理或修改组件。
- 不假设第三方 URL 修改规则是受支持 API。
- 不把所有图片一律设为 lazy；真正的首屏/LCP 图片仍需要及时发现。
- 不以牺牲明显清晰度换取未经评审的体积数字。

## 方案比较

| 方案                        | 做法                                                        | 优点                                       | 缺点 / 风险                                                    |
| --------------------------- | ----------------------------------------------------------- | ------------------------------------------ | -------------------------------------------------------------- |
| A. 只收紧 priority 数量     | 将 `idx < 10` 改为基于前 1–2 张或可见行的规则，保留当前 URL | 最小改动；能快速减少高优先级竞争           | 不解决单图尺寸过大；固定数量仍未必适配所有视口                 |
| B. 直接使用外部图源尺寸变体 | 验证图源规则后构造多个外部 URL，提供 `srcset`/`sizes`       | 无需自建图片处理服务；浏览器可响应式选择   | 第三方规则可能不稳定或无正式承诺；缓存/CORS/限流不可控         |
| C. 同源图片代理/转换层      | 后端按白名单 URL 生成或转发指定宽度的 AVIF/WebP/JPEG        | 尺寸、格式、缓存和回退可控；隐藏第三方差异 | 增加计算、存储、成本、安全和运维复杂度；必须防 SSRF 与开放代理 |

## 推荐方案

采用分阶段的 **A + 经验证后的 B/C**：

1. 先把高优先级候选从 10 张收紧到前 1–2 张，并以运行时瀑布验证。这个步骤风险低，但数量不是不可变常量；如果实测首屏有更多关键卡片，应根据证据调整。
2. 对 Bangumi 图片 URL 做能力验证。若存在稳定、文档化或长期可验证的宽度变体，优先方案 B。
3. 若外部图源无法可靠提供变体，且字节浪费在真实流量中显著，再采用受限的同源代理方案 C。代理必须只接受解析后的允许域名和枚举宽度，不接受任意目标 URL。

`AnimeCover` 最终应接收候选集合或代理基址，而不是在展示组件里猜测第三方 URL。普通网格与日历大卡片应使用不同 `sizes`，因为它们的布局宽度不同。

## 分步骤实施计划（当前不要实施代码）

1. **采集基线**
   - 在 `/anime` 的常用列表视图测试 360px、768px、1280px 及高 DPR。
   - 记录首屏可见卡片数量、LCP 元素、前 10 张封面的请求优先级、开始时间、传输字节和自然尺寸。
   - 用禁用缓存的受限网络运行至少 3 次，避免缓存掩盖问题。
2. **验证外部图源**
   - 收集 v0 `medium`、calendar `large` 和回退 URL 样本。
   - 检查响应状态、像素尺寸、MIME、缓存头、重定向、防盗链和不同宽度 URL 是否稳定。
   - 记录“已验证规则”，未验证 URL 变换不得进入实现。
3. **收紧优先级策略**
   - 设计默认前 1–2 张为 eager/high，其余 lazy/auto 或 lazy/low 的策略。
   - 评估是否需要根据布局而不是固定索引决定数量；优先选择简单且可预测的规则。
   - 保持 SSR 输出 `<img>`，让浏览器 preload scanner 能发现关键封面。
4. **设计响应式候选**
   - 根据网格断点计算卡片近似 CSS 宽度，编写普通卡片 `sizes`。
   - 为日历卡片单独测量并编写 `sizes`，不能复用普通网格的假设。
   - 候选宽度应覆盖常见 DPR，但限制档位，避免缓存碎片。
5. **若需代理，先做安全设计**
   - 仅允许明确的 Bangumi 图片主机；解析 URL 后校验协议和最终主机，阻止内网/IP/重定向逃逸。
   - 宽度、质量和格式使用枚举或严格上限；限制响应体、超时和并发。
   - 设计长期缓存键、失败回退、内容类型验证和成本监控。
6. **组件接口规划**
   - 让图片数据层返回 `src`、候选及必要元数据，`AnimeCover` 负责渲染 `srcSet`/`sizes`。
   - 保留错误占位和加载渐变；声明宽高/比例以防 CLS。
   - 不把 `fetchPriority="low"` 作为所有非关键图的硬性要求，测试 `auto` 是否更符合浏览器调度。
7. **复测和灰度**
   - 对比初始请求数、高优先级请求数、图片总字节、LCP 和首屏清晰度。
   - 若代理上线，监控命中率、上游失败、转换延迟和成本。

## 风险与取舍

- 只保留 1–2 张高优先级在超高视口下可能过于保守，因此必须按设备实测。
- 使用 `IntersectionObserver` 自制懒加载通常不如原生 `loading` 简单，本任务不建议无证据替换原生能力。
- `fetchPriority="low"` 可能让刚进入视口的图片显示偏慢；应与 `auto` 对比。
- 代理能节省客户端字节，但会增加服务端 CPU、缓存存储和安全面。
- 第三方服务条款、图片版权和热链政策需要确认。
- 响应式 URL 档位太多会降低 CDN 缓存命中率。
- 高质量大图对日历卡片可能合理，不能把普通网格结论直接套用到所有封面。

## 验证方法

- DevTools Network 按 Priority、Initiator 和 Size 分析冷加载瀑布。
- 读取 `img.currentSrc`、`naturalWidth` 与实际 CSS 宽度，计算过度取样比例。
- Lighthouse/WebPageTest 记录移动端 LCP、图片字节和关键请求链，至少运行 3 次取中位数。
- 在 2×/3× DPR 和各主要断点做截图对比，检查模糊和锯齿。
- 用 Playwright 或浏览器测试断言首屏最多只有约定数量的 `loading="eager"`/`fetchpriority="high"` 图片。
- 代理方案需要 SSRF、非法尺寸、超大响应、错误 MIME、上游超时和缓存命中测试。
- 检查图片失败时占位仍可用，页面无 CLS。

## 验收标准

- 普通列表初始 HTML 中不再有 10 张 eager/high 封面；默认最多 1–2 张，或有实测支持的明确数量。
- 关键首张封面仍能被 SSR HTML 和 preload scanner 直接发现。
- 普通网格封面具备有效 `srcset`/`sizes`，不同视口能选择不同合理尺寸。
- 日历卡片没有因复用错误 `sizes` 而明显降质。
- 外部尺寸规则有验证记录；若使用代理，安全白名单、上限、缓存与回退测试全部通过。
- 对比报告包含高优先级请求数、首屏图片字节、LCP 与视觉结果；不宣称未经测量的固定收益。
- CLS 没有回归，图片错误态和懒加载行为正常。

## 依赖 / 前置关系

- 需要可访问外部图片源的测试环境和至少一组真实 URL 样本。
- 需要明确目标浏览器、常用视口和 DPR 分布。
- 若采用代理，需要部署平台的缓存、图片转换能力、成本预算及安全评审。
- 可复用 `007-hero-image.md` 的格式矩阵和性能测量方法。
- 与 `010-calendar-n-plus-one.md` 并行时要避免把图片请求和卡片增强 API 请求混在同一网络结论中。

## 学习要点

- `loading` 决定何时加载倾向，`fetchPriority` 影响调度提示；两者不是同一概念。
- “前 N 个数据项”不等于“首屏可见 N 张”，视口高度和布局都会改变可见范围。
- 响应式图片需要候选 URL 和准确 `sizes`，仅用 CSS 缩小不会节省传输。
- 外部图片 URL 的看似规律不能替代正式能力验证。
- 图片代理是性能组件也是安全边界，必须防 SSRF、开放代理和缓存爆炸。
- 应同时测量网络字节、LCP 和视觉质量，而不是只追求更小文件。
