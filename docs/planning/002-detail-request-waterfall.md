# 002：消除详情页可选请求瀑布

## 元信息

| 字段       | 值                                                                        |
| ---------- | ------------------------------------------------------------------------- |
| 状态       | 待实施                                                                    |
| 优先级     | P0                                                                        |
| 类别       | 服务端数据加载 / 并发 / 渐进呈现                                          |
| 证据置信度 | 高：串行 `await` 可静态确认；各上游实际耗时占比和最佳拆分粒度需运行时验证 |

## 问题摘要

详情 loader 在核心 Bangumi 数据完成后，按对象属性求值顺序依次等待 Bilibili、Comicat 和 Bangumi 日志。Bilibili 的中文名/原名回退也通过循环串行尝试。结果是详情完整响应时间可能接近多个可选请求耗时之和，而不是其中最慢者；任一未被内部吞掉的失败还可能让整个详情 loader 失败。

核心详情内部的三个 Bangumi 请求已经使用 `Promise.all`，问题主要位于核心数据之后的增强数据聚合层。

## 当前证据

### 静态确认

1. `start/app/routes/anime/detail.tsx:47-51`：loader 首先 `await fetchCachedDetail(id)`，因此所有增强请求都在核心详情完成后才开始。
2. `start/app/routes/anime/detail.tsx:70-75`：返回对象中的三个 `await` 会按 JavaScript 属性求值顺序依次执行：

   ```tsx
   bilibili: await loadBilibiliMatch(...),
   comicat: await fetchComicatForAnime(keywords),
   bgmBlog: await fetchBgmSubjectBlog(id, 6),
   ```

3. `start/app/routes/anime/detail.tsx:36-44`：`loadBilibiliMatch` 使用 `for...of`，先等待一个名称搜索；仅在无匹配时再等待下一个名称搜索。这是明确的串行回退。
4. `start/app/lib/bangumi/server/detail.server.ts:49-53`：核心详情的 subject、persons、episodes 已通过 `Promise.all` 并行，不应把整个详情链路描述为完全串行。
5. `start/app/lib/bilibili/search.ts:27-46`：单次 Bilibili 搜索有 4 秒超时。
6. `start/app/lib/comicat/fetch-rss.ts:38-47` 与 `start/app/lib/bangumi/server/blog/rss.server.ts:68-77`：Comicat 和日志函数内部会把错误转为空数组；这降低了整体失败概率，但仍会等待其请求结束或超时。
7. `start/app/routes/anime/detail.tsx:94-95`：当前组件从一个完整的 `loaderData` 同时读取核心和全部可选数据，说明 UI 契约尚未分层。

### 需要运行时验证

- 冷/热缓存下四个阶段各自的 P50、P95、超时率和错误率。
- Bilibili 第一个关键词命中率，以及第二次回退带来的实际收益与额外延迟。
- 可选面板位于首屏还是滚动后区域，用户在多久后真正看到或使用它们。
- React Router 当前部署目标对流式数据、资源路由和 fetcher 的具体支持与行为。
- 并行请求是否触发第三方限流；不能假设并行越多越好。

## 工作原理 / 为什么会慢

`await` 会暂停当前异步函数，直到对应 Promise 完成。对象字面量并不会自动并行执行多个 `await`：第一个属性完成后才开始求值第二个属性，之后才是第三个。因此冷缓存近似关键路径为：

`核心详情耗时 + Bilibili 耗时 + Comicat 耗时 + 日志耗时`

Bilibili 回退又可能是：

`中文名搜索耗时 + 原名搜索耗时`

如果先创建所有 Promise 再统一等待，关键路径可接近：

`核心详情耗时 + max(Bilibili, Comicat, 日志)`

如果进一步把增强数据从主体 loader 拆出，详情主体关键路径可接近核心详情本身；可选面板随后独立完成。注意：并行化减少的是等待总时长，不会减少请求次数，并且可能提高瞬时并发。

## 影响

- 详情主体、预取完成和 SSR 响应可能被非关键上游拖慢。
- 一个慢服务会延后与它无关的面板。
- 未隔离的异常可能扩大为整页错误；当前部分函数内部吞错，但策略并不统一。
- 串行回退降低了 Bilibili 并发和无效请求数，这是它的正面取舍。
- 如果直接改成全并行，服务端峰值连接数和第三方 API 压力会增加。

这些是控制流层面的风险；当前没有实测数据证明某一个上游已经成为主要瓶颈。

## 优化目标

- 让首屏详情主体只依赖核心 Bangumi 数据。
- 可选数据互不阻塞、互不连带失败，并有清晰 loading/empty/error 状态。
- 在不必要增加请求数的前提下消除可避免的串行等待。
- 保持 Bilibili 名称回退的匹配质量，并用数据决定是否并行回退。
- 为每一类请求建立可观测耗时、结果和错误分类。

## 非目标

- 本计划不实施代码。
- 不改变第三方数据的业务含义或匹配算法正确性。
- 不要求所有可选面板必须在主体首次绘制时完成。
- 不通过无限延长超时来掩盖慢请求。
- 不承诺仅靠 `Promise.allSettled` 就解决预取放大、缓存无界或取消传播问题。

## 方案比较

### 方案 A：在现有 loader 中使用 `Promise.allSettled`

**做法**：核心详情完成后立即启动三个增强 Promise，统一 `allSettled`，成功值写入数据，失败值转为各面板的回退状态。

**优点**：

- 改动集中，类型和 UI 结构可基本保持。
- 总等待从三个耗时之和降为最慢请求耗时。
- `allSettled` 天然支持单项失败隔离。

**缺点**：

- 完整 loader 仍必须等待最慢的可选请求，主体不能提前呈现。
- 路由预取仍会触发所有增强请求。
- 瞬时并发增加，可能触发限流。
- 若只返回空值而不保留错误类型，排障能力仍然不足。

### 方案 B：可选面板独立加载

**做法**：详情 loader 只返回核心数据；Bilibili、Comicat、日志分别由资源路由/fetcher 或框架支持的流式边界加载。

**优点**：

- 主体响应不再等待可选服务。
- 每个面板可以独立配置超时、缓存、重试、错误文案和触发时机。
- 与卡片仅预取核心详情的目标一致。

**缺点**：

- 需要调整数据契约和组件结构。
- 会出现渐进加载，需要稳定占位以避免布局偏移。
- 如果三个面板一挂载就都请求，虽然主体更快，请求总量并未减少。
- 需确认所选 React Router 机制在 SSR 和客户端导航中的行为。

### 方案 C：保持单 loader，但返回框架支持的延迟/流式数据

**做法**：核心字段立即返回，可选 Promise 交给路由流式传输和局部 Suspense/Await 边界。

**优点**：

- 保留路由级数据声明，主体可先输出。
- 比多个资源端点更集中。

**缺点**：

- 强依赖当前 React Router 版本和 Cloudflare 适配器对流式响应的支持。
- 中断、序列化和错误边界更复杂。
- 预取可能仍启动所有 Promise，不能自动解决无效工作。

## 推荐方案

推荐 **方案 B 为目标架构，方案 A 作为低风险过渡**：

1. 先把现有三个增强请求改为同时启动并用 `Promise.allSettled` 统一归一化结果，快速移除明确瀑布并隔离异常。
2. 随后将 `bilibili`、`comicat`、`bgmBlog` 从核心 loader 契约移出，建立面板级加载边界。
3. Bilibili 的两个名称回退暂时保持串行，因为“第一个命中便不发第二个请求”能节省请求；只有在测得回退经常发生且延迟收益值得额外请求后，才考虑并行搜索并定义匹配优先级。

## 分步骤实施计划（当前不要实施代码）

1. **测量现有瀑布**
   - 为核心详情、Bilibili、Comicat、日志分别记录开始时间、结束时间、缓存状态和结果类别。
   - 覆盖冷缓存、热缓存、上游慢响应、上游失败场景。
2. **定义结果模型**
   - 为每个可选面板定义 `success | empty | timeout | aborted | upstream-error`。
   - 区分“没有匹配”和“请求失败”，避免都折叠为 `null`/`[]` 后无法诊断。
3. **过渡并行化**
   - 核心详情完成后先创建三个 Promise，再 `Promise.allSettled`。
   - 把 rejected 原因映射为结构化面板状态；不要让单项异常抛出整页。
   - 配置总并发观测，确认没有明显限流回归。
4. **拆分核心和增强契约**
   - 详情 loader 仅返回 `DetailPayload` 及主体必要派生值。
   - 三个面板分别建立资源端点或 fetcher 封装，使用稳定的 subject ID/规范名称作为输入。
   - 面板组件各自处理 loading、empty、error 和 retry。
5. **确定触发时机**
   - 首屏内且高使用率的面板可在主体加载后立即请求。
   - 折叠区或首屏外面板可在展开/接近视口时请求。
   - 防止重新渲染重复触发，并与 single-flight 缓存协同。
6. **处理 Bilibili 回退**
   - 统计第一个关键词命中率和第二关键词增量命中率。
   - 若保留串行，确保共享总超时和取消信号；若并行，定义中文名优先和取消落败请求的策略。
7. **回归类型与 UI**
   - 更新 `AnimeDetailData` 和面板 props，不再假设可选数据同步存在。
   - 为局部失败提供可理解文案，不把正常“无结果”显示成错误。
8. **添加测试**
   - 单元测试并行启动、结果归一化和 Bilibili 回退顺序。
   - 集成测试验证任一可选上游超时不阻塞主体。

## 风险与取舍

- 全并行会缩短等待但提高瞬时并发，需观察限流和 Worker 资源。
- `allSettled` 若无结构化日志，容易把真实故障静默吞掉。
- 面板独立请求可能增加同源 HTTP 往返；可通过缓存、HTTP/2/3 和批量策略权衡。
- 渐进呈现可能引起布局偏移，应预留稳定高度或使用不会推挤主体的占位。
- Bilibili 双关键词并行可能把请求数接近翻倍，不能仅为降低少量尾延迟盲目采用。
- 流式方案在本地 Node 与 Cloudflare 的表现可能不同，必须在目标环境验证。

## 验证方法

### 静态验证

- 确认三个可选 Promise 在统一等待前已创建，而不是在数组中继续延迟串行创建。
- 确认主体类型不再要求可选数据已完成。
- 确认每个 rejected 结果被映射为明确状态并记录可观测错误。
- 确认请求 signal 从路由传播到所有底层 fetch。

### 运行时验证

- 用可控 mock 分别令三个上游延迟 100、300、500 ms：过渡方案总等待应接近最慢项而非三者之和。
- 令一个上游超时/500，验证主体和其他面板仍成功。
- 记录详情主体可见时间、完整面板完成时间、上游并发峰值和请求总数。
- 在 Cloudflare 预览环境复测流式或 fetcher 行为，不只依赖本地开发服务器。
- 检查预取：卡片 intent 是否只获取核心数据。

## 验收标准

- 现有 loader 中不存在三个增强数据的属性级串行 `await`。
- 详情主体可在 Bilibili、Comicat、日志任一慢或失败时正常显示。
- 每个可选面板都有独立 loading、empty、error 状态。
- mock 延迟测试证明并行阶段不再按耗时相加；最终拆分后主体时间不包含可选上游耗时。
- Bilibili 回退策略有命中率和请求成本依据，而非仅凭直觉改为并行。
- 没有新增未捕获 Promise rejection 或整页错误回归。

## 学习要点

- 对象字面量中的多个 `await` 仍按求值顺序串行，不会自动并发。
- `Promise.all` 追求全部成功，`Promise.allSettled` 适合互相独立、允许局部失败的增强数据。
- 并发优化解决关键路径，不等于减少请求或降低上游成本。
- 最有效的性能边界通常是把关键数据和可选数据分离，而非只把所有请求塞进一个更大的 `Promise.all`。
- 串行回退有节省请求的价值；是否并行应由回退率、延迟和限流共同决定。
