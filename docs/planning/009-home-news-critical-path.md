## 问题摘要

首页 loader 在返回页面数据前 `await fetchNewsFeed(24)`。新闻面板位于 Hero 之后，但整个首页 SSR 数据仍依赖新闻聚合完成。聚合内部并发请求多个外部源，并使用 `Promise.all` 等待全部结果；单源请求配置了 8 秒超时。因此在缓存未命中时，首页 TTFB 可能被最慢源的尾延迟拉长，即使新闻并非首屏最关键内容。

现有 10 分钟缓存是模块内 `Map`，属于进程/Worker 实例内存缓存。它能改善同一存活实例的后续命中，但不能静态保证跨实例、冷启动或重新部署后命中。实际是否出现接近 8 秒的首页延迟、哪些源最慢、当前部署实例复用情况，都需要运行时观测。

## 当前证据

### 已静态确认

1. `start/app/routes/home.tsx:30-32` 的首页 loader `await fetchNewsFeed(24)` 后才返回 `{ news }`。
2. `start/app/routes/home.tsx:217-218` 才渲染 `NewsPanel`；新闻面板位于前面的 Hero 和分类内容之后。
3. `start/app/lib/news/fetch-news.ts:21-22` 创建模块级新闻缓存。
4. `start/app/lib/news/fetch-news.ts:50-68` 在缓存未命中时用 `Promise.all` 并发等待 Google、巴哈姆特、Bangumi Blog、RSSHub 和 AniNews 等结果。
5. `start/app/lib/news/constants.ts:1-2` 将新闻缓存 TTL 设置为 10 分钟。
6. `start/app/lib/news/constants.ts:47-48` 将通用新闻请求超时设为 8,000 ms。
7. `start/app/lib/news/fetch-google-news.ts:53-59`、`start/app/lib/news/fetch-bahamut.ts:19-27`、`start/app/lib/news/fetch-rsshub.ts:18-28` 和 `start/app/lib/news/fetch-aninews.ts:19-25` 均在外部请求上使用该超时。
8. `start/app/lib/cache.ts:10-17` 明确说明 `createCache` 是进程内内存缓存，底层为模块内 `Map`；注释也提示 Cloudflare 部署可替换为 KV。
9. `start/app/lib/cache.ts:35-45` 的 `withCache` 在未命中时会等待 fetcher 完成后才写入并返回，没有 stale-while-revalidate 行为。

### 需要运行时验证

- 首页冷缓存和热缓存的 TTFB 分布（p50/p75/p95），以及各新闻源的实际耗时。
- 当前各源是否都在内部捕获错误；`Promise.all` 中任一未捕获拒绝会影响整体结果，需要故障注入确认。
- Cloudflare 部署中的实例复用、缓存命中率和冷启动比例。
- 新闻内容对首页 SEO、爬虫抓取和分享预览的真实价值。
- React Router 7.17 + 当前 Cloudflare 适配器能否按预期流式传递 loader Promise 和 Suspense 边界。
- 新闻占位到内容替换是否会产生 CLS 或可感知闪烁。

## 工作原理 / 为什么会慢

SSR 的首字节通常要等路由 loader 产生可序列化结果。当前 loader 显式 `await` 新闻聚合，因此 Hero 的 HTML 即使不依赖新闻，也无法先独立完成这条数据路径。

`Promise.all` 能把多个请求从串行改为并行，但整体完成时间仍约等于最慢任务的完成时间；并发解决“总和延迟”，不解决“尾延迟”。当某个源接近 8 秒超时，聚合就可能等待接近该上限。这里的“可能”来自控制流静态分析，不能当作线上已经发生 8 秒 TTFB。

进程内缓存只对当前实例生命周期有效。边缘平台可能启动多个隔离实例，用户请求也可能落到不同实例；因此 10 分钟 TTL 不等于全局 10 分钟内都命中。共享缓存可以扩大命中范围，但如果缓存未命中时仍同步刷新，冷请求仍会阻塞。

stale-while-revalidate 的思想是：有旧但仍可接受的数据时立即返回旧值，在后台更新；流式/独立加载的思想是：先发送 Hero 和页面框架，新闻完成后再填充。两者解决不同层次的问题，通常可以组合。

## 影响

- **TTFB/FCP**：非首屏新闻可能延迟整个首页 HTML；实际幅度待测。
- **可靠性**：外部 RSS/API 波动被带入首页关键路径。
- **资源利用**：多实例各自刷新会重复打外部源，增加限流风险。
- **SEO**：完全客户端加载可能让部分爬虫看不到新闻，需明确取舍。
- **布局稳定性**：异步插入面板若无固定骨架可能造成 CLS。

## 优化目标

1. Hero 和首页主体不再必须等待新闻源冷请求完成才开始响应。
2. 使用跨实例可共享的缓存，并支持 stale-while-revalidate 或等价策略。
3. 外部源故障不应使首页主体不可用。
4. 保留合理的新闻 SEO 可见性：缓存命中时优先 SSR 新闻，冷启动时允许稳定占位/流式补全。
5. 为新闻面板预留稳定空间，避免异步内容导致 CLS。
6. 建立源级耗时、错误率、缓存命中和首页 TTFB 的可观测性。

## 非目标

- 不改新闻排序、去重、中文转换或展示设计。
- 不在本计划阶段修改 loader、缓存或组件。
- 不承诺所有爬虫都执行客户端 JavaScript。
- 不用无限期陈旧数据换取速度；必须定义 fresh/stale/expired 窗口。
- 不把“并发请求”误写成“不会被慢源阻塞”。

## 方案比较

| 方案                                                    | 做法                                                                            | 首屏速度                            | SEO                                      | 布局稳定           | 复杂度 / 风险                                        |
| ------------------------------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------- | ---------------------------------------- | ------------------ | ---------------------------------------------------- |
| A. 共享缓存 + stale-while-revalidate，loader 仍返回新闻 | 使用 Cloudflare Cache API/KV 等保存 feed；命中 fresh/stale 时快速 SSR，后台刷新 | 热/陈旧命中快，真正冷启动仍可能等待 | 最好，常见请求含完整新闻 HTML            | 最稳定             | 需要共享存储、锁/去重和过期策略；冷 miss 未完全解决  |
| B. loader 返回延迟 Promise，SSR 流式填充 Suspense       | 首先输出页面壳和 Hero，新闻 Promise 完成后流式补齐                              | 冷 miss 也可先响应                  | 支持流式的爬虫可能看到完整内容，但需验证 | 使用固定骨架可稳定 | 依赖框架/适配器流式能力；错误边界和 hydration 更复杂 |
| C. 新闻完全独立客户端请求 `/api/news`                   | 首页不在 loader 请求新闻，hydration 后加载                                      | 首页关键路径最短                    | 最弱，初始 HTML 无新闻                   | 需精确骨架         | 实现直观但有二次请求、闪烁和无 JS 降级问题           |

## 推荐方案

推荐 **A + B 的混合方案**：

- 先建立跨实例共享的 fresh/stale 缓存。fresh 命中直接 SSR；stale 命中立即 SSR 旧数据并异步刷新。
- 对真正的冷 miss 使用框架支持的流式 Promise与固定高度骨架，让 Hero 不等待新闻。只有在当前 Cloudflare SSR 链路验证流式不可用时，才退回方案 C。
- 保留上一次成功数据，源级失败只标记状态，不清空整个 feed。刷新应带并发去重/短锁，避免多个实例同时击穿外部源。

该方案兼顾 SEO 与布局稳定：大多数缓存命中请求仍有新闻 HTML，冷启动先得到页面主体，新闻区域使用结构相同的骨架。不能直接写死“SEO 无损”，必须用抓取后的实际 HTML 和流式行为验证。

## 分步骤实施计划（当前不要实施代码）

1. **建立性能与可靠性基线**
   - 为首页 loader、`fetchNewsFeed` 和每个源记录耗时、结果数、超时/错误类型。
   - 区分 fresh hit、进程内 hit、共享缓存 hit、stale hit 和 cold miss。
   - 采集生产或等价环境 TTFB p50/p75/p95，避免只看本地单次结果。
2. **确认 SEO 与内容时效需求**
   - 明确新闻允许的 fresh TTL、stale 窗口和 hard expiry，例如 10 分钟 fresh、数小时 stale；最终数值由产品决定。
   - 用搜索抓取/无 JS 请求确认新闻是否必须存在于初始 HTML。
3. **选择共享缓存介质**
   - 比较 Cloudflare Cache API、KV 或现有平台缓存能力的延迟、一致性、配额和成本。
   - 设计包含 feed 版本和 limit 的缓存键；现有键 `news:v6:${limit}` 的版本语义可延续。
   - 存储数据、生成时间、过期时间和源状态，便于判断 stale。
4. **设计刷新与防击穿**
   - fresh：立即返回。
   - stale：立即返回旧值，用 `waitUntil` 或平台等价机制后台刷新。
   - cold miss：单实例/跨实例尽可能去重；设置总预算，不让一个慢源无限拖延。
   - 刷新失败时保留最近一次成功值，并记录错误，不覆盖成空数据。
5. **验证流式能力**
   - 在 React Router 7.17 的生产构建和 Cloudflare 运行时做最小实验，确认 loader Promise、Suspense、错误边界及 HTML flush 时机。
   - 检查代理/CDN 是否缓冲响应；本地开发服务器结果不能替代部署验证。
6. **设计新闻 UI 边界**
   - 为加载态、部分成功、完全失败和 stale 状态设计稳定骨架/提示。
   - 骨架尺寸应接近最终 `NewsPanel` 首屏高度，避免内容到达时推移页脚。
   - 错误只影响新闻边界，不影响 Hero 和导航。
7. **调整数据路径**
   - 缓存命中时让 SSR 直接获得数据。
   - 冷 miss 时返回延迟数据并由 Suspense 渲染；若部署验证失败，则改用 `/api/news` 客户端加载并保留 `<noscript>`/可访问降级策略。
8. **逐步上线与观测**
   - 先上线指标，再上线共享缓存，最后上线流式边界，分开评估贡献。
   - 监控 TTFB、缓存命中率、stale 使用率、刷新失败率、各源尾延迟和 CLS。

## 风险与取舍

- 共享缓存带来数据陈旧和失效复杂度；新闻场景通常可接受有限 stale，但需产品确认。
- KV 可能具有最终一致性和读取成本；Cache API 的跨区域行为也需按平台文档验证。
- 后台刷新必须正确挂接运行时生命周期，否则响应结束后任务可能被取消。
- 流式 SSR 可能被 CDN、代理或开发工具缓冲，必须端到端验证。
- 完全客户端加载实现简单，但降低初始 HTML 内容和无 JS 体验。
- 固定骨架过高会留下空白，过低会产生 CLS。
- `Promise.all` 的错误传播要逐源审计；不能为了速度吞掉所有错误而失去可观测性。

## 验证方法

- 使用 Server-Timing 或结构化日志测量 loader、缓存层和各源耗时。
- 对 fresh、stale、cold miss、单源超时、全部源失败做集成测试。
- 使用 `curl`/浏览器抓取响应流，确认首个 HTML chunk 是否在新闻完成前到达。
- 在生产构建下运行 Lighthouse/WebPageTest，至少 3 次比较 TTFB、FCP、LCP、CLS。
- 查看禁用 JavaScript时的首页和搜索抓取 HTML，评估 SEO/可用性。
- 并发压测 cold miss，确认不会对外部源产生刷新风暴。
- 验证 stale 数据带生成时间，刷新失败时仍返回最近成功内容。

## 验收标准

- Hero/主体响应不再在 cold miss 时无条件等待所有新闻源完成；通过响应流或客户端独立加载证据确认。
- fresh/stale 新闻缓存能跨 Worker 实例共享，且有记录可证明命中类别。
- 单个新闻源达到 8 秒超时或失败时，首页主体仍成功返回。
- 新闻区域有稳定骨架或已有缓存 HTML，异步补全不造成可见 CLS 回归。
- 报告首页 TTFB p50/p75/p95、缓存命中率和源级耗时；不把静态推断当线上收益。
- SEO 决策有抓取 HTML 证据：明确哪些缓存状态下新闻存在于初始/流式 HTML。
- 刷新失败不会用空结果覆盖最近成功缓存，且错误可观测。

## 依赖 / 前置关系

- 需要 Cloudflare 运行时的共享缓存能力、绑定或 Cache API 方案。
- 需要可部署的 staging 环境验证真正的流式行为。
- 需要产品确认新闻时效与 SEO 权重。
- 需要基础日志/指标能力，最好在行为改动前上线。
- 若选择客户端兜底，可复用 `start/app/routes.ts:8` 已注册的 `/api/news` 路由，但仍需检查其缓存与错误语义。

## 学习要点

- `Promise.all` 并发执行，但整体延迟仍由最慢任务决定。
- 位于页面下方的数据也可能因 loader 依赖而进入 SSR 关键路径。
- 进程内缓存、跨实例缓存和浏览器/CDN 缓存是不同层次，命中范围不同。
- stale-while-revalidate 优化缓存命中路径，流式渲染优化冷 miss 的响应路径。
- 性能、SEO 和布局稳定不是非此即彼；缓存 SSR + 冷启动流式可以取得平衡。
- 任何“首页更快”的结论都应由 TTFB/LCP/CLS 和真实缓存状态数据支持。
