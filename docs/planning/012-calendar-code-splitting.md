**结论：**

1. 静态导入确实让非日历列表也带上日历代码——问题成立，但体积是「中小」不是「巨大冗余」。
2. 整体 `lazy(AnimeSchedule)`（方案 A）上限大约数 KiB～约 9 KiB gzip，还要付 SSR/Suspense/预取成本；按文档停止条件，**暂不优先整体拆分**。
3. 若以后动手，更划算的是方案 B：只拆 `AnimeCalendarPicker` / 周总览 / `SummaryModal`（交互后才需要），核心日视图保持同步。

## 问题摘要

动画主布局静态导入 `AnimeSchedule`，但只在 loader 数据包含非空 `schedule` 时渲染它。普通排行、搜索或列表视图不需要日历 UI，却可能因静态模块图承担 `AnimeSchedule` 及其日期选择、周总览、卡片增强和图标代码的初始依赖成本。

动态 import 有潜在收益，但不能仅凭文件较大就实施。日历可能是重要直达页面；盲目懒加载会增加一个网络往返、Suspense fallback 和闪烁。React Router SSR、React 19 Suspense 与 Cloudflare 适配器如何处理该动态边界，也需要用生产构建验证。应先用 bundle analyzer 确认日历模块在非日历路由的真实初始占比，再选择组件级、子功能级或路由级拆分。

6. `start/package.json:5-10` 提供生产 build 和 typecheck 脚本；`start/package.json:30-40` 当前未配置专用 bundle analyzer。

### 需要构建/运行时验证

- `AnimeSchedule`、`AnimeCalendarPicker`、`AnimeWeekOverview`、`anime-card-extra` 及图标各自的 raw/gzip/brotli 体积。
- 普通 `/anime` 列表的初始 chunk 是否确实包含这些模块，或 bundler 是否已经做了其他拆分。
- 动态 import 后的 chunk 请求时机、缓存复用和首次日历渲染延迟。
- 服务端能否在直达日历 URL 时等待/流式渲染 lazy 组件，以及客户端 hydration 是否稳定。
- 日历页面的 SEO需求；列表型工具页面可能不依赖正文 SEO，但不能未经确认假设。
- 日历入口的用户占比和从站内点击到达与直接访问的比例。

## 工作原理 / 为什么会慢

静态 import 让 bundler 在构建时把模块纳入同步依赖图。即使 JSX 分支在运行时不执行，模块通常仍需要下载和解析；tree-shaking 不能删除运行时可能为真的完整分支。

动态 `import()` 会建立异步边界，使非日历视图可以不下载日历代码。但直接访问日历时，浏览器可能需要先拿布局 chunk，再发现并请求日历 chunk，形成额外瀑布。SSR 若能在服务器加载模块并流式输出，可以改善内容可见性，但客户端仍需对应 chunk 完成 hydration。

拆得太细也会增加请求、边界和状态管理复杂度。例如只在点击后才需要的日期选择器很适合延后，而日视图主体是日历直达页的核心内容，过度延后会更容易产生闪烁。代码分割应围绕“用户何时需要功能”，而不是按文件机械切割。

## 影响

- **非日历视图**：可能下载和解析未使用的日历功能代码；实际字节待分析。
- **日历直达**：动态拆分可能增加首次内容等待和 fallback。
- **SSR/SEO**：错误边界设计可能让初始 HTML 缺少核心日历内容。
- **缓存**：频繁在列表和日历间切换的用户通常只需下载一次异步 chunk，后续可复用。
- **维护**：更多 Suspense/错误边界会提高测试与故障处理成本。

## 优化目标

1. 在 analyzer 证明收益有意义的前提下，让非日历列表不加载日历专属代码。
2. 保持日历直达页的 SSR 可用性、稳定占位和无 hydration 错误。
3. 使用预取减少从站内日历入口点击后的异步 chunk 等待。
4. 优先延后真正交互后才需要的子功能，避免为了小收益拆分核心首屏内容。
5. 以各路由初始总 JS、日历可见时间、LCP/INP 和闪烁情况共同验收。

## 非目标

- 不改变日历数据 loader、日期逻辑、周总览功能或卡片 UI。
- 不在本计划阶段添加 `lazy()`、`Suspense` 或修改路由。
- 不因文件行数多就认定 bundle 大。
- 不接受“chunk 数增加”本身作为优化成功指标。
- 不把网络 N+1 优化混入本任务；该问题由 `010-calendar-n-plus-one.md` 单独规划。

## 方案比较

| 方案                                                                   | 拆分边界                                                | 非日历收益                   | 日历直达体验                    | 复杂度 / 风险                                                        |
| ---------------------------------------------------------------------- | ------------------------------------------------------- | ---------------------------- | ------------------------------- | -------------------------------------------------------------------- |
| A. 整体动态导入 `AnimeSchedule`                                        | 布局只在 schedule 分支加载完整日历组件                  | 最大，能移出所有日历专属依赖 | 可能出现额外请求和主体 fallback | 中；需 SSR/Suspense/错误边界和预取                                   |
| B. 保持 `AnimeSchedule` 同步，只拆日期选择器、周总览、简介弹窗等子功能 | 核心日视图仍同步，交互/特定模式按需加载                 | 中到低                       | 最稳定；常用日视图几乎不变      | 中；边界较多但各自语义清楚                                           |
| C. 按独立路由/布局拆日历视图                                           | 将 calendar 变成独立 route module，数据与 UI 同边界加载 | 潜在最大且路由语义清楚       | 可利用路由级 SSR 和预取         | 高；当前通过 query `view=calendar`，需改路由/链接/状态，超出最小改动 |

## 推荐方案

采取“**先分析，后分层拆分**”策略：

1. 若 analyzer 显示完整 `AnimeSchedule` 对非日历初始 gzip/执行成本贡献显著，优先方案 A，但必须确保直达日历的 SSR 和稳定 fallback 通过验证。
2. 无论是否整体拆分，都优先评估方案 B 中真正低频的日期选择器、周总览和 `SummaryModal`。这些功能仅在打开选择器、切换 overview 或展开简介时需要，更符合按交互拆分原则。
3. 暂不推荐方案 C。当前日历由 query 参数选择，改为独立路由会影响 URL、loader、链接和状态，除非未来产品明确要把日历作为独立页面。

设置停止条件：如果 analyzer 证明从非日历视图移出的 gzip 很小，或动态边界使日历直达明显闪烁，则只拆低频子功能，甚至保持现状。性能收益必须大于额外复杂度。

## 分步骤实施计划（当前不要实施代码）

1. **建立 bundle 基线**
   - 与 `011-site-nav-bundle.md` 共用 Vite/Rollup analyzer。
   - 分别记录普通列表、搜索/排行和日历视图的初始 chunk 集合、raw/gzip/brotli 和模块组成。
   - 确认静态导入是否真正使日历依赖进入非日历首屏。
2. **建立体验基线**
   - 测量直达日历和站内切换日历时的 HTML 内容、FCP/LCP、可交互时间和请求瀑布。
   - 记录日历首屏结构，设计尺寸一致的 fallback，防止 CLS。
3. **验证 SSR/Suspense 能力**
   - 用最小 PoC 测试 React `lazy`/动态 import 在 React Router 7.17、React 19 和 Cloudflare 生产环境的服务端输出。
   - 检查服务器是否输出日历正文或 fallback、响应是否流式、客户端是否有 hydration warning。
   - 模拟 chunk 加载失败，确认错误边界可重试且不破坏整个动画布局。
4. **评估拆分边界**
   - 统计完整 `AnimeSchedule` 与三个低频子功能的独立贡献。
   - 依据用户路径选择整体拆分或只拆子功能，避免同一依赖被多个异步 chunk 重复打包。
   - 检查共享图标、`AnimeCover`、utils 是否留在公共 chunk 更合理。
5. **设计整体动态导入（若达门槛）**
   - 只在 `schedule?.length` 分支创建/渲染 lazy 组件，确保普通列表不触发 import。
   - 使用与最终日历高度和结构相近的 skeleton，而不是空白或通用 spinner。
   - 为异步 chunk 设置局部错误边界和重试入口。
6. **设计预取策略**
   - 用户 hover/focus/touch 日历入口或路由 intent 时预取日历模块。
   - 不在所有页面无条件 modulepreload，否则会抵消拆分收益。
   - 直达日历可由 SSR/module preload 提前发现，具体方式以构建产物验证。
7. **设计子功能拆分**
   - `AnimeCalendarPicker` 在 `pickerOpen` 前后按需加载，并提供即时按钮反馈。
   - `AnimeWeekOverview` 可在 URL 已是 overview 时立即加载，在日视图不加载。
   - `SummaryModal` 在用户意图或首次点击时加载，同时保留可访问的加载状态。
8. **实施顺序规划**
   - 先拆一个低频子功能并验证构建与 SSR模式。
   - 再决定是否拆完整 `AnimeSchedule`，不要一次引入多个边界导致难以归因。
   - 与 N+1 请求改造分批发布。
9. **复测与决策**
   - 比较非日历初始总 JS、日历额外请求、日历内容可见时间、CLS 和首次交互。
   - 若收益未达到门槛或直达体验变差，回退整体拆分，保留低频子功能拆分。

## 风险与取舍

- 日历 chunk 若较小，新增异步请求和 Suspense 复杂度可能得不偿失。
- 服务端能加载 lazy 模块不代表 CDN 一定实时 flush；需要端到端测试。
- fallback 与最终内容尺寸不一致会产生 CLS 或视觉闪烁。
- 过度预取会让非日历用户仍下载代码，抵消收益。
- 拆分多个相互依赖组件可能造成共享代码重复或碎片化。
- 动态 import 失败需要可恢复 UI，否则原来同步可用的功能会变成网络故障点。
- 日历直达用户会承担额外 chunk；这是以非日历多数用户收益换取的成本，需用访问分布判断。

## 验证方法

- Bundle analyzer 比较每条路由初始模块图和异步 chunk 内容，检查重复模块。
- DevTools Network 在普通列表确认没有请求日历 chunk，在直达/点击日历时确认请求时机。
- 生产 SSR 环境抓取禁用 JS 的 HTML，确认日历正文或可接受降级。
- 慢速网络/CPU 下观察 skeleton、内容替换、LCP 和首次日历交互。
- Playwright 覆盖普通列表、直达日历、站内预取、overview、日期选择、弹窗和 chunk 加载失败。
- 检查控制台 hydration mismatch、动态导入错误和未捕获 Suspense。
- Lighthouse/WebPageTest 多次运行，报告非日历初始 JS 与日历可见时间的中位数。

## 验收标准

- 有 analyzer 证据说明哪些日历模块进入非日历初始图，以及拆分后移出了多少实际 gzip/brotli 与执行代码。
- 普通列表、搜索和排行视图不请求已确定的日历专属异步 chunk。
- 日历直达和站内进入均有稳定 skeleton/SSR 内容，无明显布局闪烁和 hydration warning。
- 站内日历入口的 intent 预取有效，但非意图用户不会无条件下载日历 chunk。
- 日期选择、周总览、卡片增强和简介弹窗功能无回归，异步加载失败可局部恢复。
- 报告同时包含非日历收益和日历代价；若收益不足，按停止条件保留同步实现。
- 未将 `010-calendar-n-plus-one.md` 的网络请求变化混入本次 bundle 收益结论。

## 学习要点

- JSX 条件渲染不会自动产生代码分割；静态 import 的模块通常仍在同步依赖图中。
- 动态 import 优化的是“不需要该功能的用户”，同时会让需要它的用户承担额外加载边界。
- 最好的拆分边界通常对应用户意图：打开选择器、切换 overview、展开弹窗。
- SSR、Suspense、CDN flush 和客户端 hydration 是一条端到端链路，任何一层都可能改变体验。
- 预取应由真实意图触发；无条件预取会把异步代码重新变成初始成本。
- 代码分割的成功标准是总字节、执行成本和用户体验改善，不是 chunk 数量增加。
