## 问题摘要

详情 loader 为了只修改 `subject.images` 中的 URL，先对整个 `DetailPayload` 执行 `JSON.stringify`/`JSON.parse` 深克隆。该方式复制范围远大于实际修改范围，还隐式依赖 payload 完全可 JSON 序列化。更直接的做法是只对从根节点到 `images` 的对象路径做浅层不可变复制，或者在缓存写入前统一规范化图片 URL。

这属于可维护性与潜在性能优化，而不是已确认的线上瓶颈。收益大小取决于 payload 大小、请求频率和运行环境，必须通过 benchmark 才能量化。

## 当前证据

### 已静态确认

- `start/app/routes/anime/detail.tsx:27-34`：详情数据同时包含 `DetailPayload` 以及 Bilibili、Comicat、博客扩展数据，并存在客户端内存缓存。
- `start/app/routes/anime/detail.tsx:47-54`：loader 先调用 `fetchCachedDetail(id)`，随后用 `JSON.parse(JSON.stringify(data))` 深克隆整个 `DetailPayload`，注释说明目的是避免修改共享缓存。
- `start/app/routes/anime/detail.tsx:56-64`：克隆后实际原地修改的只有 `clonedData.subject.images` 各字段，将 URL 传给 `toHttps`。
- `start/app/routes/anime/detail.tsx:66-75`：后续读取规范化后的 subject，并展开整个 cloned payload 返回附加数据。
- `start/app/lib/cache.ts:19-31`：内存缓存的 `get` 直接返回已存对象引用，`set` 也直接保存传入引用，因此避免修改缓存对象本身是合理约束。

### 需要运行时验证

- `DetailPayload` 在典型、P95 和最大条目下的序列化字节数与对象规模。
- JSON 深克隆在 Node、本地 Wrangler 和 Cloudflare 实际运行时中的耗时与内存分配。
- 浅复制后是否存在其他下游代码继续修改嵌套字段。
- 图片 URL 规范化是否已经在其他入口发生，是否适合上移到缓存边界。

## 工作原理 / 原因

对象展开只复制一层。要在不修改缓存对象的前提下替换 `images`，只需复制会被改变的引用链：根 `data`、`subject`、`images`。未改变的 episodes、tags 等子树可以安全共享，只要后续把 payload 当作只读数据。

JSON 往返会遍历并重新分配整个对象图，还会丢弃 `undefined`、函数和 symbol，并把 Date 等特殊类型转成普通 JSON 表示。当前 payload 很可能本来就来自 JSON API，因此未必已经出现语义损坏；但依赖这种偶然特性不如显式复制清晰。

另一种思路是在 `fetchCachedDetail` 写入缓存前就把 HTTP 图片规范化。这样每次读取都无需重复转换，但会改变缓存内数据的规范形式，影响所有调用者，实施前需审查边界。

## 影响

- 每次 loader 执行都可能产生与整个 payload 大小成正比的 CPU 与临时内存成本。
- 深克隆掩盖了真正的修改范围，让维护者难以判断哪些字段必须隔离。
- 若未来 payload 引入非 JSON 类型，JSON 克隆可能静默改变数据。
- 目前没有 benchmark，不能断言该代码已造成明显延迟或 Cloudflare CPU 超限。

## 优化目标

1. 保证缓存返回的 `data`、`data.subject` 和 `data.subject.images` 不被修改。
2. 仅复制需要改变的对象路径，保持返回结构和类型不变。
3. URL 规范化逻辑集中、可测试、对空值安全。
4. 用 benchmark 说明优化收益；若收益很小，也以代码意图清晰作为主要价值。

## 非目标

- 不重写详情抓取与缓存系统。
- 不递归冻结整个 payload。
- 不在没有证据时替换所有项目中的 JSON 序列化。
- 不改变图片字段的 HTTPS 转换规则或失败回退语义。

## 方案比较

### 方案 A：沿修改路径做浅层不可变复制

创建新的 `images`，对每个 URL 调用 `toHttps`；再创建新的 `subject` 和根 payload，其他未修改子树保持引用共享。

**优点：** 改动局部；复杂度和分配量与实际修改范围匹配；类型意图清楚；容易验证缓存未被改写。  
**缺点：** 依赖后续代码遵守只读约定；若未来还要修改其他深层字段，需要继续显式复制对应路径。

### 方案 B：在抓取/缓存写入前统一规范化

把图片 HTTPS 转换放到 `fetchCachedDetail` 的数据规范化阶段，缓存中始终保存规范化结果。

**优点：** 每个缓存项通常只转换一次；所有消费者看到一致数据；loader 更简洁。  
**缺点：** 改变共享缓存契约和更多调用路径；需要确认是否有消费者需要原始 URL；测试范围更大。

### 方案 C：使用 `structuredClone`

以标准 API 替换 JSON 往返。

**优点：** 对更多内建类型语义更正确，代码简短。  
**缺点：** 仍深拷贝整个 payload，未解决复制范围过大的根因；不同运行时兼容性还需确认。

## 推荐方案

近期采用方案 A。它直接表达“只替换图片映射，同时保护缓存对象”的意图，改动范围最小。将 URL 映射提取为纯函数，可独立测试输入不变性、空图片和各种协议。

方案 B 可作为后续架构优化：仅当 benchmark 显示重复转换有意义，且调用方审查证明缓存内统一 HTTPS 不会破坏语义时再实施。方案 C 不推荐作为最终优化，因为它只是更正确的全量深拷贝。

## 分步骤实施计划（当前不实施代码）

1. 确认 `DetailPayload["subject"]["images"]` 的完整类型、可选字段和 `toHttps` 对空值/非 HTTP URL 的行为。
2. 搜索 `fetchCachedDetail` 的所有调用者，确认缓存对象是否被其他路径修改或依赖原始图片 URL。
3. 为当前行为建立测试样本：有 images、无 images、部分空字段、HTTP、HTTPS。
4. 提取纯规范化函数，返回新 images 对象，不修改传入对象。
5. 在 loader 中只复制根 payload、subject 和 images；其余字段保持原值/引用。
6. 添加不变性断言：调用后原始缓存对象及其图片字段保持不变，返回值具有规范化 URL。
7. 用代表性小/中/大 payload 比较 JSON 深克隆与浅复制的执行时间和分配；预热后多轮测量，记录环境。
8. 运行类型检查、构建及详情页回归；若收益不显著，也保留基于语义清晰和类型安全的结论，不夸大性能。
9. 若考虑方案 B，另开变更审查缓存契约，不与局部替换同时扩大范围。

## 风险与取舍

- 共享未修改的嵌套子树意味着后续代码若原地修改它们，仍可能污染缓存；应通过只读类型/代码审查约束，而非盲目深拷贝。
- 手写字段复制可能漏掉未来新增图片尺寸；最好按现有 images 键进行映射，并让 TypeScript 检查。
- 上移到缓存边界会让原始数据不可直接获取，需确认调试与其他消费者需求。
- 微型 benchmark 容易受 JIT、GC 与样本大小影响，应报告范围而非单次数字。

## 验证方法

- 在测试中保存原对象和嵌套对象引用/值，执行规范化后确认原值未改变。
- 检查返回根对象、subject、images 是新引用，未修改子树仍可共享引用。
- 验证 HTTP 被升级、HTTPS 保持不变、缺失 images 不报错。
- 对同一 payload 多次执行，确认结果幂等。
- 运行代表性 payload benchmark，并分别在本地 Node 与 Wrangler 环境采样；Cloudflare 生产数据若不可得，应明确标注。
- 运行 `npm run typecheck`、`npm run build`，并手动打开多个详情页验证图片。

## 验收标准

- loader 不再通过 JSON 往返克隆整个 `DetailPayload`。
- 缓存中的原始对象及 images 不被修改。
- 返回 payload 除图片 URL 规范化外与当前行为一致。
- 空图片、部分字段和已是 HTTPS 的输入均正确处理。
- 测试覆盖不变性和转换语义。
- 任何性能结论都附带 benchmark 环境与数据；没有数据时只描述为潜在收益。

## 依赖 / 前置关系

- 无外部依赖。
- 自动化测试可复用 `018-testing-and-lint.md` 规划的测试框架。

## 学习要点

- 不可变更新通常只需复制从根到变更点的引用链。
- JSON 序列化不是通用深克隆工具，其类型语义有限。
- 缓存返回共享引用时，调用方必须避免原地修改，或在明确边界规范化数据。
- 性能优化应区分“复杂度上更合理”和“已测得用户收益”。
