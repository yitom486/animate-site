# 007：首页 Hero 图片格式与响应式优化

## 问题摘要

首页首屏使用的 `portal-hero.png` 实际是一个扩展名为 `.png` 的 JPEG 文件，大小为 1,166,539 bytes，尺寸为 1024×1024。它在首屏 Hero 区域中铺满容器，但只以 `opacity-32` 显示，并被高不透明度渐变进一步覆盖。当前页面没有提供 AVIF/WebP、响应式候选尺寸，也没有明确声明图片尺寸。

这意味着浏览器可能为一个视觉权重较低、很可能属于装饰用途的背景下载约 1.11 MiB 原始资源。它是否是当前页面的 LCP 元素、下载是否阻塞更关键资源、不同设备实际浪费多少字节，都不能仅凭源码确定，必须通过浏览器运行时数据验证。

## 当前证据

### 已静态确认

1. `start/public/assets/portal-hero.png` 是二进制资源，没有可引用的源码行号；本地使用 `file` 与字节计数确认：
   - 实际内容类型：JPEG/JFIF，而不是 PNG；
   - 像素尺寸：1024×1024；
   - 文件大小：1,166,539 bytes。
2. `start/app/routes/home.tsx:91-96` 将该资源放在首页第一个主要内容区中，并使用绝对定位、`object-cover`、`opacity-32` 和 `mix-blend-luminosity`。
3. `start/app/routes/home.tsx:97-98` 在图片上方叠加了覆盖整个区域的高不透明度渐变和底部渐变，降低了原图细节的视觉贡献。
4. `start/app/routes/home.tsx:92-96` 只有单一 `src` 和普通 `alt`；没有 `<picture>`、`srcSet`、`sizes`、`width` 或 `height`。

### 需要运行时验证

- 该图片是否被浏览器选为 LCP 元素；Hero 内的标题也可能成为 LCP。
- 图片请求对 LCP、FCP、首屏总传输量和主线程图片解码耗时的贡献。
- 1024×1024 原图在手机、平板和宽屏上的实际显示尺寸及裁剪比例。
- CDN/托管层是否依据扩展名发送错误的 `Content-Type`，以及缓存头是否理想。
- AVIF/WebP 在项目目标浏览器中的实际压缩收益；不能只根据格式名称预估固定百分比。

## 工作原理 / 为什么会慢

浏览器看到首屏 `<img>` 后会尽早发起请求。当前只有一个候选 URL，因此无论设备视口、设备像素比和实际布局宽度如何，浏览器都只能下载完整的 1,166,539-byte 文件。手机可能只需要较小的图片，宽屏则可能把 1024 像素图片放大并裁剪。

JPEG 内容使用 `.png` 扩展名不会自动增加图片字节，但会造成格式语义混乱，并可能影响服务器 MIME 配置、运维排查和后续优化工具的处理。现代有损 WebP/AVIF通常能为这类插画提供更好的体积—质量平衡，但具体质量参数必须用视觉对比决定。

即使图片透明度很低，CSS 仍然需要下载、解码并合成整张图片；视觉上“淡”不等于网络或解码成本低。若该图片只是营造氛围，非空 `alt="次元航行者"` 还可能让读屏用户把它当作有信息意义的内容重复理解。

## 影响

- **网络**：冷缓存首屏可能下载约 1.11 MiB 图片；实际线上传输量取决于 HTTP 压缩与图片本身，图片通常不会因 gzip 获得明显收益。
- **渲染**：下载和解码可能竞争首屏关键资源；是否影响 LCP 需实测。
- **响应式质量**：小屏可能过度下载，大屏可能出现放大或不理想裁剪。
- **可维护性**：扩展名与真实编码不一致，容易误导开发者和构建工具。
- **可访问性**：如果图片纯装饰，当前非空替代文本会制造无必要的语义噪声。

## 优化目标

1. 让扩展名、MIME 和实际编码一致。
2. 为常见显示宽度提供 AVIF/WebP 响应式候选，并保留可靠回退。
3. 在不显著降低当前视觉质量的前提下，明显降低首屏图片传输字节。
4. 根据内容意图确定装饰语义；若不承载信息，使用空 `alt` 并从辅助技术语义中移除。
5. 保持 Hero 尺寸稳定，不引入 CLS。
6. 以移动端和桌面端实测为准评估 LCP，而不是预先宣称固定提升。

## 非目标

- 不重新设计首页 Hero 的布局、文案或配色。
- 不在本计划阶段生成图片、改 JSX 或修改部署配置。
- 不因为图片位于首屏就直接添加 preload；只有确认它是关键 LCP 资源且预加载不会挤占更关键请求后才考虑。
- 不承诺未经实测的体积缩减比例或 LCP 毫秒收益。

## 方案比较

| 方案                                          | 做法                                                                  | 优点                                                     | 缺点 / 风险                                                                 |
| --------------------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------- |
| A. 只纠正格式并压缩单文件                     | 重新编码为正确扩展名的 JPEG 或 WebP，继续使用单一 `src`               | 改动小，容易回滚，立即消除格式错配                       | 所有设备仍下载同一尺寸；无法同时兼顾手机字节和高 DPR/宽屏质量               |
| B. `<picture>` + 多尺寸 AVIF/WebP + JPEG 回退 | 生成例如 480/768/1024/1440 宽度候选，使用 `srcSet`、`sizes`，声明尺寸 | 浏览器按视口和格式能力选择；可兼顾传输量、兼容性和清晰度 | 增加资源生成、缓存和质量验收工作；`sizes` 写错会选错资源                    |
| C. CSS 背景图 + media query/image-set         | 把装饰图片移到背景，按断点切换格式和尺寸                              | 装饰语义自然，不进入可访问性树                           | 响应式选择、加载优先级和回退控制通常不如 `<picture>` 清晰；性能观测更不直观 |

## 推荐方案

采用 **方案 B**，并把该图按“装饰性视觉层”处理：保留 `<img>`/`<picture>` 以获得可靠的响应式选择和加载控制，但将替代文本设为空；如团队确认图片确实表达标题之外的独立信息，再保留准确的非空替代文本。

先根据 Hero 在真实断点下的 rendered width 和 DPR 设计候选尺寸，不机械生成过多档位。建议优先试验 480、768、1024、1440 宽度，实际档位由 DevTools 观测决定。AVIF、WebP 的质量参数应通过截图对比，特别关注渐变覆盖后仍可见的边缘、肤色和色带。保留一个编码正确的 JPEG 作为兼容回退。

不要默认把 `fetchPriority="high"` 或 preload 加到图片上。先确认 LCP 候选和请求优先级；如果 Hero 标题才是 LCP，主动抬高装饰图优先级可能适得其反。

## 分步骤实施计划（当前不要实施代码）

1. **建立基线**
   - 在生产构建上分别以移动端和桌面端配置运行 Lighthouse/WebPageTest。
   - 记录 LCP 元素、图片请求开始时间、响应大小、解码时间、缓存头和首屏截图。
   - 在 DevTools Elements 中记录图片于主要断点的 CSS 尺寸与实际 `currentSrc` 需求。
2. **确认语义**
   - 与设计/产品确认图片是否传递标题和文案之外的信息。
   - 若只是氛围背景，规划 `alt=""`；必要时加 `aria-hidden="true"`，避免重复语义。
3. **制定图片矩阵**
   - 按实测显示宽度选择 3–4 个候选尺寸；考虑 DPR，但避免生成没有使用场景的超大资源。
   - 为每个尺寸生成 AVIF、WebP，并保留正确扩展名的 JPEG 回退。
   - 记录编码器版本、质量参数和输出字节，方便重复构建。
4. **视觉质量评审**
   - 在低透明度、混合模式和渐变覆盖的最终页面中比较，而不是只看原图。
   - 检查色带、块状伪影、人物边缘和宽屏裁剪。
5. **规划组件标记**
   - 使用 `<picture>` 的 AVIF/WebP `<source>` 与 JPEG `<img>`。
   - 为 `<img>` 设置与源图比例一致的 `width`/`height`；现有绝对定位仍可由 CSS 覆盖布局尺寸。
   - 写出与 Hero 最大宽度和断点一致的 `sizes`，不能简单写 `100vw`。
6. **部署层核对**
   - 确认各扩展名返回正确 `Content-Type`、长期缓存头和可版本化 URL。
   - 若文件名不含内容哈希，规划安全的缓存失效方式。
7. **复测与决策**
   - 使用相同环境重跑基线测试，比较传输字节、LCP 和请求优先级。
   - 只有运行时证据表明图片发现过晚且确为 LCP 时，才试验 preload 或高优先级。

## 风险与取舍

- AVIF 通常更小但编码慢，部分图像在相同主观质量下可能出现不同伪影。
- 过多候选会增加仓库体积和维护成本；候选过少则降低响应式收益。
- 错误的 `sizes` 可能让浏览器下载比当前更大的资源。
- 改为空替代文本前必须确认它确实不承载信息。
- 若更换文件名，需要注意缓存、引用和部署同步；不能保留“新内容、旧 MIME”的半完成状态。
- 大幅压缩后若视觉差异只在覆盖层下不可见，这是可接受的工程取舍，但需要设计确认。

## 验证方法

- `file`/图片元数据工具确认每个文件的实际编码、尺寸和扩展名一致。
- 浏览器 Network 面板检查不同视口/DPR 下的 `currentSrc`、传输大小、优先级和 MIME。
- Lighthouse 或 WebPageTest 各运行至少 3 次，使用中位数比较 LCP，避免把网络波动当收益。
- 在禁用缓存和启用缓存两种情况下测试。
- 对 360px、768px、1280px、宽屏和高 DPR 场景做截图回归。
- 使用屏幕阅读器或 Accessibility Tree 确认装饰图片不被朗读。
- 监控 CLS，确保尺寸声明和绝对定位没有引入布局变化。

## 验收标准

- 图片文件扩展名、实际编码和响应 `Content-Type` 一致。
- 至少提供 AVIF/WebP 与兼容回退，并有基于实测布局编写的 `srcSet`/`sizes`。
- 360px 与桌面视口会选择不同且合理的候选，不再都下载原始 1,166,539-byte 文件。
- 最差常用断点下视觉质量经人工评审可接受，没有明显色带、模糊或错误裁剪。
- 图片语义已书面确认；若为装饰，Accessibility Tree 中没有无意义的“次元航行者”朗读项。
- 生产构建的对比报告包含 LCP、首屏图片字节和请求瀑布；只报告实测结果，不将静态推断写成已实现收益。
- 无新增 CLS 回归。

## 依赖 / 前置关系

- 需要可重复的生产构建与性能测试环境。
- 需要设计/产品确认图片的语义和可接受视觉质量。
- 若使用自动图片流水线，需要先决定由仓库脚本、CI 还是 CDN 负责派生图。
- 与 `008-cover-loading.md` 的响应式图片策略可共享命名、质量参数和观测方法，但 Hero 为本地静态资源，不依赖外部封面代理。

## 学习要点

- 文件扩展名不是图片真实格式；应同时核对魔数、MIME 和编码。
- CSS 透明度只改变显示结果，不减少下载、解码和合成成本。
- `srcSet` 提供候选，`sizes` 告诉浏览器布局需求；二者必须一起正确使用。
- 首屏图片不等于一定要 preload。资源优先级应由 LCP 和瀑布证据驱动。
- 装饰图片应使用空替代文本；有信息意义的图片才需要描述性 `alt`。
- 性能规划要把“静态可确认的浪费可能性”与“运行时已测得的用户指标影响”分开。
