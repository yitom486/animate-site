## 问题摘要

博客无限加载把“服务端已经没有下一页”和“本次请求失败”都编码为 `hasMore=false`。失败后点击重试时，事件处理器先调用 `setHasMore(true)`，随后立即调用旧闭包中的 `loadMore()`；该闭包仍读取到 `hasMore=false`，因而在入口处直接返回。这是可由 React 状态更新与闭包语义静态确定的重试缺陷。

另一个独立议题是长列表性能：条目永久累积；每次加载都合并整个历史数组并全量去重；渲染层始终映射全部条目。数据规模足够大时可能增加内存、去重和 DOM 成本，但实际阈值与用户影响尚未 profile。近期应先修复重试，长期再根据数据决定分页、窗口化或保留上限。

## 工作原理 / 原因

React 的 state setter 会安排下一次 render，而不会立即修改当前函数闭包中的变量。错误 render 中的 `loadMore` 捕获了 `hasMore=false`；同一点击回调中的 `setHasMore(true)` 只安排更新，紧接着调用的仍是旧函数，因此命中 `if (loading || !hasMore) return`。

根因是 `hasMore` 同时表示两件不同的事：分页终止事实和请求暂时失败。请求失败并不能证明没有下一页。把二者分开后，重试无需先伪造 `hasMore=true`。

长列表方面，第 n 次加载会创建 `[...prev, ...data.items]`，再遍历整个累计数组去重；随着总条目数增长，单次合并工作近似与累计条目数成正比。与此同时 React 仍协调并保留全部卡片 DOM。风险在模型上存在，但是否值得引入虚拟化取决于真实规模和 profile。

## 影响

- 用户遇到一次网络或服务端错误后，点击“加载失败，点此重试”可能没有任何网络请求，无法从页面内恢复。
- 把错误写成 `hasMore=false` 使 UI 状态含义模糊，后续自动加载与重试更容易互相干扰。
- 超长会话可能出现更高内存、较慢 commit 或滚动掉帧；当前没有实测数据，不能断言已发生严重性能问题。
- 直接引入虚拟化会增加可访问性、动态高度、滚动恢复和 SSR 的复杂度。

## 优化目标

1. 请求失败后重试必定能够重新请求同一“下一页”。
2. “加载中”“加载失败”“已到底”互斥且语义清晰。
3. 避免重复并发请求和页码跳跃。
4. 先以最小改动恢复正确性，再用数据决定长列表策略。
5. 保持跨页去重与现有卡片顺序。

## 非目标

- 不在近期修复中改写 Bangumi HTML 抓取器。
- 不默认引入虚拟列表依赖。
- 不把无限滚动改成全新的产品交互，除非性能数据或可访问性评审支持。
- 不通过吞掉错误来制造“重试成功”的假象。

## 方案比较

### 方案 A：最小修复，错误时保留 `hasMore`

`catch` 只记录错误，不把 `hasMore` 改为 `false`；重试按钮直接调用 `loadMore`。`hasMore=false` 只由成功响应中的分页事实设置。

**优点：** 改动小、根因明确、容易回归；不会依赖 state setter 立即生效。  
**缺点：** 多个布尔状态仍可能形成不合理组合；并发与请求身份管理仍较分散。

### 方案 B：显式请求状态机 / reducer

用 `idle | loading | error | exhausted` 表示加载状态，页码只在成功后推进；请求函数接收明确页码，失败保留待重试页。

**优点：** 状态互斥；适合测试重试、并发和竞态；长期可维护性更好。  
**缺点：** 对当前简单页面改动较大；若没有测试支撑，迁移本身可能引入行为差异。

### 方案 C：立即引入虚拟化或切回显式分页

窗口化只渲染可视区域，或限制页面只保留单页/若干页。

**优点：** 能从结构上控制 DOM 和内存；显式分页对 SSR、可分享 URL 和可访问性更简单。  
**缺点：** 动态卡片高度、滚动定位、返回恢复、SEO/SSR 需要额外设计；在未测得瓶颈前可能过度工程化。

## 推荐方案

分两阶段处理：

1. **近期正确性：** 先采用方案 A，并补充针对“失败后重试”的回归测试。若实施时发现并发竞态明显，再小步演进为方案 B，而不是一次重写。
2. **长期性能：** 先 profile。只有当真实长会话出现明显 DOM、内存或帧率问题时，才在方案 C 中选择窗口化、显式分页或“仅保留最近 N 页”。优先评估显式“加载更多”与分页，因为它们比动态高度虚拟化更简单。

去重可同步评估增量 `Set`，但不要在没有数据时声称它会带来显著用户收益。

9. 运行类型检查、构建和浏览器回归。

## 风险与取舍

- 保留 `hasMore=true` 后，哨兵仍在可视区域时可能自动再次触发；需确保错误态下只允许用户显式重试，或明确自动重试策略。
- `loading` state 对同一事件循环内的重复调用不是锁；如实测出现并发，应用 ref/request token 防护。
- 增量 `Set` 需要与 `items` 生命周期同步，处理 loaderData 变化和页面重置。
- 虚拟化会改变浏览器查找、屏幕阅读器连续阅读和返回滚动位置体验。
- 限制历史页会降低用户向上回看能力，需要产品层面取舍。

## 验证方法

- 单元/组件测试模拟：失败 → 显示错误 → 点击重试 → 发出同一下一页请求 → 成功追加。
- 验证失败前后的 `page` 不变，成功后只增加一次。
- 模拟最后一页与空页，确保显示“没有更多了”且观察器不再请求。
- 模拟跨页重复 ID，确保顺序稳定且无重复 key。
- 在慢网下快速滚动和连点，检查 Network 面板不存在重复并发页请求。
- 用 Performance 与 Memory 面板对固定页数场景采样；长期方案必须引用测量结果。
- 运行 `npm run typecheck`、`npm run build`，以及届时新增的目标测试。

## 验收标准

- 请求失败后点击一次重试会产生一次实际网络请求。
- 失败不会被错误地解释为“没有更多”。
- 页码只在成功响应后推进，重复触发不会跳页或重复追加。
- 最后一页仍能稳定进入 exhausted/无更多状态。
- 近期修复不要求引入虚拟化。
- 若实施长期优化，必须有优化前后同场景数据，并证明没有破坏滚动、可访问性与返回恢复。

## 依赖 / 前置关系

- 近期重试修复无外部依赖。
- 自动化回归测试可依赖 `018-testing-and-lint.md` 中测试基础设施；测试基础设施未完成前至少进行可重复的浏览器 mock 验证。
- 长期列表方案依赖真实或合成大数据 profile 以及产品对分页/无限滚动的选择。

## 学习要点

- React state 更新不会同步改变当前闭包中的值。
- “请求失败”与“数据耗尽”是不同状态，不应共用一个布尔值。
- 无限列表的算法和 DOM 成本会随累计数据增长，但是否优化必须由测量决定。
- 正确性补丁与架构/性能改造分阶段发布，能降低回归范围。
