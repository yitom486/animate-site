## 问题摘要

全局 CSS 同时导入 Geist Variable、JetBrains Mono 和 Noto Serif SC 三套 Fontsource 字体。给定的生产构建统计为：字体产物 210 个文件、原始总计约 7.36 MB；CSS 为 220,675 bytes raw / 73,761 bytes gzip。

这些数字说明构建输出和 CSS 声明值得精简，但不能把 7.36 MB 直接说成“每位用户都会下载 7.36 MB”。Fontsource 的字体 CSS 通常使用 `unicode-range` 切分字符范围，浏览器只会为页面实际字符选择匹配范围，并通常只选择支持/需要的格式与字重。真正的传输量受页面文本、字重、浏览器、缓存和路由影响，必须通过 Network/Performance 实测。

## 工作原理 / 为什么会慢

Fontsource 的包入口会导入一组 `@font-face` 规则。字体家族、字重、风格、字符子集和文件格式的组合会产生多个构建产物。中文字体覆盖字符极多，常按 `unicode-range` 分成很多文件，所以“文件数量”和“构建总原始大小”会很醒目。

浏览器处理流程通常是：

1. 下载包含 `@font-face` 的 CSS。
2. 根据当前页面出现的字符、匹配到的字体家族/字重/style 和 `unicode-range`，选择需要的字体文件。
3. 只下载匹配资源；不匹配的分片仍存在于构建目录，但不会必然传输。
4. 新路由出现新字符或新字重时，可能继续下载其他分片。

因此存在三类不同成本：

- **CSS 解析/传输成本**：大量 `@font-face` 声明即使不下载所有字体，也会增大 CSS。
- **构建/部署成本**：210 个资源和 7.36 MB 影响构建产物、上传和缓存管理。
- **用户网络成本**：只等于该会话真正请求的字体文件，必须实测，不能用构建总量代替。

## 影响

- 全局入口让所有路由都解析三套字体声明。
- 首屏匹配字体文件可能与关键 CSS、图片争抢网络。
- 字体加载时机和 fallback 度量差异可能造成文本闪烁或布局偏移。
- 大量构建资源增加部署和缓存复杂度。
- 过度裁剪中文字符会导致部分动态内容回退到系统字体，视觉不一致甚至缺字。
- 使用系统字体可显著减少网络成本，但会改变品牌视觉和跨平台一致性。

当前不能声称浏览器实际下载了全部 7.36 MB，也不能在没有性能记录的情况下声称字体已经是 LCP 主因。

## 优化目标

- 减少全局字体 CSS 声明、构建字体文件数和实际会话传输量。
- 仅保留 UI 真正使用的家族、字重、style 和字符范围。
- 动态中文、日文内容不缺字，并有合理系统 fallback。
- 避免明显 FOIT/CLS，维持可接受的视觉层级。
- 建立可重复的构建与浏览器字体体积报告。

## 非目标

- 本计划不实施代码。
- 不以“删除所有 Web Font”为默认结论。
- 不把构建目录总大小等同于单次页面下载量。
- 不仅为减少文件数就合并成一个巨大的全字符字体。
- 不对动态第三方文本做不完整的固定字形子集后宣称覆盖充分。

## 方案比较

### 方案 A：按实际字重和字符子集精确导入 Fontsource CSS

**做法**：不再使用三个包的宽泛默认入口；根据使用清单导入具体 weight/style/subset CSS。对 Geist 保留需要的 variable 范围；JetBrains Mono 只保留实际字重；Noto Serif SC 保留业务所需字重与必要字符范围。具体导入路径需先依据当前包版本导出清单验证。

**优点**：

- 保持现有视觉设计，迁移风险相对低。
- 能减少无用 `@font-face`、字体文件和 CSS。
- 继续利用 Fontsource 的 `unicode-range` 分片。

**缺点**：

- 中文动态内容可能触发较多分片，实际下载收益需测量。
- Fontsource 不同包/版本的导入路径和 subset 支持不同。
- 权重使用散落在 Tailwind class 和浏览器 synthetic bold 中，盘点不完整会导致回退。

### 方案 B：减少家族数量，优先系统字体

**做法**：例如移除 JetBrains Mono Web Font，使用系统 monospace；或将大段中文正文改用系统中文 serif，只在品牌标题使用 Noto Serif SC。

**优点**：

- 用户网络收益最大，CSS 和构建产物也明显减少。
- 系统字体通常无需等待下载。

**缺点**：

- 跨平台字形差异增大，品牌风格改变。
- 系统中文字体在 Windows、macOS、Android 上差别明显。
- 需要视觉验收，不只是技术改动。

### 方案 C：路由/组件作用域加载字体

**做法**：将特定字体 CSS 从全局入口移到真正需要它的路由或组件样式，让 Vite/React Router 有机会代码分割；配合 preload 仅加载当前首屏字体。

**优点**：

- 不访问相关路由的用户无需解析或下载该字体。
- 可让日志正文、品牌标题等使用独立策略。

**缺点**：

- 当前首页和 Anime 路由都使用 serif/mono，简单拆路由收益可能有限。
- CSS chunk 与字体加载延后可能增加 FOUT。
- 需要验证构建器是否确实将字体 CSS/资产按路由分割，不能只看源码位置。

### 方案 D：自建静态字形子集

**做法**：用 fonttools/glyphhanger 等基于已知字符生成更小字体，动态内容回退系统字体或维护增量子集。

**优点**：

- 对固定品牌文案可获得极小体积。
- 能精确控制字形和格式。

**缺点**：

- Bangumi 标题、简介、用户名等字符不可预知，固定子集很容易缺字。
- 增加构建工具、字体许可审计和维护成本。
- 不适合直接覆盖全站动态正文。

## 推荐方案

采用低风险的分阶段组合：

1. **先实施方案 A**：建立字重/字符/路由使用清单，使用当前 Fontsource 版本支持的精确入口，删除未使用 style 和 weight。
2. **再评估方案 B**：优先考虑将 JetBrains Mono 改为系统 monospace，或只为少量品牌标题保留 Noto Serif SC；是否接受由视觉对比决定。
3. **对确实只在少数页面使用的字体采用方案 C**。由于首页和 Anime 已共同使用 serif/mono，必须以构建分包和实际 Network 结果证明收益。
4. **方案 D 仅用于固定、可枚举的品牌文案**，不用于动态条目正文。

## 分步骤实施计划（当前不要实施代码）

1. **固定基线方法**
   - 使用锁文件安装依赖并执行生产构建。
   - 输出字体文件数量、按家族/大小分组、CSS raw/gzip/brotli。
   - 把命令和结果保存为可比较报告。
2. **做字体使用清单**
   - 搜索 `font-sans`、`font-serif`、`font-mono` 及 CSS `font-family`。
   - 记录每处可达的实际 `font-weight`、style 和路由。
   - 检查浏览器 computed style，确认 `@theme` 两处 `--font-sans` 的最终结果。
3. **做浏览器请求基线**
   - 清空缓存后分别访问首页、列表、详情、日志。
   - 导出 HAR，按字体 family、range、size、initiator 汇总。
   - 记录 CSS 和字体是否阻塞文本、FCP/LCP/CLS。
4. **核对 Fontsource 包能力**
   - 查看锁定版本的 package exports/CSS 文件，确认可用的具体 weight、latin、latin-ext、中文分片入口。
   - 不凭其他版本文档猜测导入路径。
5. **精简 Geist**
   - 确认 variable font 是否覆盖实际使用权重。
   - 只保留所需字符范围和正常 style；若无 italic 使用则不引入。
6. **精简 JetBrains Mono**
   - 盘点是否只用于少量标签和数字。
   - 比较保留单一常用字重与改用系统 monospace 的视觉/体积。
7. **精简 Noto Serif SC**
   - 区分品牌标题、正文和动态第三方文本。
   - 只声明实际需要的字重；避免因 `font-bold` 无对应字体而下载额外权重或依赖不可控 synthetic bold。
   - 保留系统中文 serif fallback，测试简中、日文、罕见字符和标点。
8. **评估作用域**
   - 尝试把只在特定路由需要的字体 CSS 移入路由样式。
   - 生产构建后确认 CSS chunk 和字体资产是否真正按需加载。
9. **优化加载策略**
   - 检查 `font-display` 设置是否符合体验目标。
   - 只 preload 首屏确定会用且收益经测量成立的字体，避免 preload 反向浪费。
   - 字体响应设置长期 immutable 缓存（带内容哈希时）。
10. **回归与报告**
    - 重跑构建统计和 HAR。
    - 同时报告构建总量、实际首访传输量、缓存复访和视觉指标，避免只挑有利数字。

## 风险与取舍

- 删除字重可能触发 synthetic bold，视觉质量变化但不一定容易在代码审查中发现。
- 中文 unicode-range 分片数量多并不等于用户全下；只追求文件数可能做出错误优化。
- 过度 preload 会抢占带宽，尤其与封面图竞争。
- 路由作用域加载会让首次进入新路由时才下载字体，可能增加闪烁。
- 系统字体减少网络成本但跨平台不一致，需要产品/视觉接受。
- 自定义子集需确认字体许可、保留版权信息，并为动态字符提供 fallback。

## 验证方法

### 静态与构建验证

- 比较精简前后生产 CSS raw/gzip/brotli。
- 比较字体文件数和按家族的原始总大小，但明确这不是用户下载量。
- 检查生成 CSS 的 `@font-face`、weight、style、format、unicode-range。
- 检查构建不存在 404 引用或重复字体声明。

### 运行时验证

- Chrome DevTools Network 过滤 Font，记录每个测试路由冷缓存实际 transferred bytes。
- Coverage 检查字体 CSS 规则使用情况，结合 computed style 确认真实 family/weight。
- Performance/Lighthouse 多次测试 FCP、LCP、CLS；本地结果只作方向参考。
- 模拟 Slow 4G 和禁用缓存，观察 FOIT/FOUT。
- 覆盖简体中文、日文标题、拉丁字符、数字、标点和罕见字符，确认无缺字。
- 在 Windows、macOS、Android 至少各做一次视觉抽查，尤其是系统 fallback 方案。

## 验收标准

- 三套字体不再通过宽泛默认入口无条件全局导入，或每个保留入口都有经测量的理由。
- 生产字体文件数、CSS gzip 和至少两个代表路由的冷缓存字体传输量较基线下降；具体阈值在复核基线后设定。
- 报告明确区分“构建产物总大小”和“浏览器实际下载量”。
- 主要页面无缺字、不可接受的 synthetic weight、明显 FOIT 或 CLS 回归。
- 动态中文/日文内容有经过验证的 fallback。
- preload 仅用于真实首屏命中的字体资源，Network 中无明显无用 preload。
- 构建统计可由文档化命令重复生成。

## 学习要点

- 构建产物总大小、CSS 大小和用户实际传输量是三个不同指标。
- `unicode-range` 允许浏览器按页面字符选择字体分片，因此大量输出文件不代表全部下载。
- 字体优化应从 family × weight × style × subset × route 五个维度盘点。
- 中文动态内容不适合盲目固定字形子集；可靠 fallback 与体积同样重要。
- preload 只对高置信度关键资源有益，错误 preload 会让性能更差。
