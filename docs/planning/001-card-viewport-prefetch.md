## 问题摘要

`AnimeCard` 对每个详情链接统一使用 `prefetch="viewport"`。在常见列表页中，一页最多可包含 42 张卡片；卡片进入视口时，React Router 可以提前请求对应详情路由数据。详情路由不仅读取 Bangumi 核心详情，还聚合 Bilibili、Comicat 和 Bangumi 日志等可选外部数据。

因此，一次浏览列表可能在用户尚未表达点击意图时触发多条昂贵详情请求。这里的风险是“可能造成预取放大”，而不是已经证明“一定同时发出 42 个请求”：实际数量会受视口尺寸、滚动、React Router 的去重策略、缓存命中和浏览器调度影响，必须运行时验证。

## 当前证据

### 静态确认

1. `start/app/components/anime-card.tsx:20-23`：每张卡片的 `Link` 都固定设置了 `prefetch="viewport"`。

   ```tsx
   <Link
     to={to}
     prefetch="viewport"
   ```

2. `start/app/routes/anime/layout.tsx:190-199`：普通列表会把 `items` 中的每一项渲染为 `AnimeCard`，没有按卡片位置调整预取策略。
3. `start/app/lib/bangumi/constants.ts:7-16`：默认列表页按 7 列 × 6 行计算，`LIST_PAGE_SIZE` 为 42；搜索类视图另有 20 条上限，因此“42”是常见普通列表的上限，不代表所有视图都固定为 42。
4. `start/app/routes/anime/detail.tsx:47-75`：详情 loader 先获取核心详情，然后返回 Bilibili 匹配、Comicat 和 Bangumi 日志三类可选数据。
5. `start/app/lib/bangumi/server/detail.server.ts:43-61`：核心详情本身还会并行请求条目、人员和章节三个 Bangumi 接口，并在完成后写入内存缓存。
6. `start/app/routes/anime/layout.tsx:152-156` 和 `start/app/routes/anime/layout.tsx:213-218`：项目其他导航链接已使用 `prefetch="intent"`，说明该策略与现有代码风格兼容。

### 需要运行时验证

- 首屏在不同视口下实际进入 viewport 的卡片数。
- 页面首次打开和连续滚动时产生的详情数据请求数、取消数及重复数。
- 预取是否执行完整详情 loader，以及各运行环境中的去重和缓存行为。
- 被预取详情中最终真正点击的比例，即预取命中率。
- 对 Bangumi、Bilibili、Comicat 和 RSS 上游的请求放大倍数。
- 移动网络、节流网络和 Cloudflare 多实例环境下的带宽、CPU 时间及尾延迟。

## 工作原理 / 为什么会慢

`viewport` 预取以“链接进入视口”为信号。网格页面会同时显示多张卡片，滚动又会持续让新卡片进入视口，所以一个弱意图信号可以扩散成许多路由数据请求。

每次详情 loader 的冷缓存路径大致是：

1. 获取 Bangumi 核心详情；其中条目、人员和章节为三个并行外部请求。
2. 核心数据返回后，再执行 Bilibili 搜索、Comicat RSS 匹配和 Bangumi 条目日志请求。
3. loader 的完整结果准备好后，预取才算完成。

即使并行化能降低单个详情的等待时间，也不会减少请求总量。若多张卡片同时预取，外部连接数、服务端并发、缓存写入和失败重试压力都会增加。缓存可以降低重复请求，却不能保证首次预取的低成本；在无界、进程内缓存下，也不能假设不同 Worker 实例共享命中。

## 影响

可能影响包括：

- 用户未点击的详情占用流量，尤其对移动网络不友好。
- 有价值的列表图片、CSS 或真实导航请求与推测性详情请求争抢连接和带宽。
- 服务端及第三方 API 瞬时并发升高，放大限流和超时风险。
- 大量预取结果进入内存缓存，增加缓存条目数量。
- 真正点击时可能因命中预取而更快，这是当前策略的主要收益。

以上影响方向可由代码推导，但严重程度尚未实测，不能直接宣称它已经造成某个具体的 LCP、流量或错误率回归。

## 优化目标

- 显著减少无点击意图时的详情路由预取数量。
- 保留鼠标悬停、键盘聚焦或触摸交互后的快速导航体验。
- 让预取优先获取首屏必需的核心详情，而不是被可选面板拖住。
- 记录请求数、预取命中率和导航延迟，基于数据决定是否进一步调整。
- 不因优化而破坏返回列表参数、活动卡片状态或无障碍键盘导航。

## 非目标

- 本计划不立即修改代码。
- 不取消所有预取，也不把“零后台请求”作为目标。
- 不在本项中重写所有详情数据源或 UI。
- 不以隐藏错误、降低数据正确性来换取表面速度。
- 不假设 42 张卡片会在所有设备上同时触发预取。

## 方案比较

### 方案 A：把卡片统一改为 `prefetch="intent"`

**做法**：仅在 hover、focus 等用户意图出现时预取完整详情路由。

**优点**：

- 改动小，符合项目内其他链接的现有用法。
- 能直接抑制滚动导致的大面积推测请求。
- 键盘 focus 仍可触发预取，保留无障碍场景。

**缺点**：

- 触摸设备的意图窗口可能很短，预取收益低于桌面端。
- 仍然预取完整 loader，可选外部数据依旧会参与。
- 快速点击时可能来不及完成预取。

### 方案 B：保留有限 viewport 预取，但只给少量高概率卡片

**做法**：例如仅首行或前 N 张卡使用 `viewport`，其余使用 `intent`；N 由运行时数据决定。

**优点**：

- 首屏热门卡片仍有较高概率在点击前准备完毕。
- 比全量 viewport 更可控。

**缺点**：

- 需要为 `AnimeCard` 增加策略参数，并决定合理阈值。
- 排名靠前不等于用户一定点击，仍存在浪费。
- 响应式列数变化会让“首行”定义复杂化。

### 方案 C：拆分核心详情和可选面板数据

**做法**：路由导航/预取只获取条目、人员、章节等首屏核心数据；Bilibili、Comicat 和日志由独立资源请求或面板级加载器按需获取。

**优点**：

- 从根本上降低每次预取的成本和故障面。
- 可选上游变慢不会阻塞详情主体。
- 为不同面板设置独立超时、缓存和错误 UI 更自然。

**缺点**：

- 涉及 loader 数据结构、组件状态和错误处理，改动明显大于方案 A。
- 导航后面板会渐进出现，需要避免布局跳动。
- 请求总数不一定减少，只是延后并按需触发；需配合可见性或展开策略。

## 推荐方案

采用分阶段的 **A + C**：

1. 先将全部卡片从 `viewport` 改为 `intent`，快速消除最明显的请求放大入口。
2. 再把详情拆为“核心数据”和“可选面板数据”，使任何预取都只承担导航所需的核心成本。
3. 完成测量后，如果首屏点击延迟仍明显，再小范围实验方案 B，而不是直接恢复全量 viewport。

该组合优先控制请求总量与故障隔离，同时保留基于真实数据恢复有限积极预取的空间。

## 分步骤实施计划（当前不要实施代码）

1. **建立基线**
   - 在浏览器 Network 面板区分 document、route data 和外部请求。
   - 分别记录桌面首屏、移动首屏、滚动一整页但不点击、滚动后点击四种场景。
   - 统计详情预取数、上游调用数、传输量、预取命中率、点击到主体可见时间。
2. **收紧触发策略**
   - 为 `AnimeCard` 增加显式可配置的预取策略，默认使用 `intent`。
   - 保持 `Link` 的 `to`、搜索参数和键盘行为不变。
   - 为未来有限 viewport 实验预留调用方参数，但暂不启用。
3. **定义核心详情契约**
   - 明确主体首屏真正需要的字段：`subject`、必要的 `staff`、必要的 `episodes`。
   - 将 `bilibili`、`comicat`、`bgmBlog` 标记为可选面板数据，定义各自 loading/empty/error 状态。
4. **拆分数据路径**
   - 保留详情路由 loader 返回核心数据。
   - 为每个可选面板建立独立资源路由或 fetcher 调用，并传播导航取消信号。
   - 仅在面板将要展示、详情已打开或用户展开时请求；是否使用可见性触发需通过交互设计确定。
5. **完善缓存和失败隔离**
   - 核心与可选数据使用不同 TTL 和缓存键。
   - 同一详情的并发请求使用 single-flight，避免 intent 抖动造成重复抓取。
   - 可选面板失败不能让详情主体导航失败。
6. **灰度比较**
   - 对比 `viewport` 基线与 `intent + 核心预取` 的请求量和导航 P50/P95。
   - 若桌面快速点击退化明显，实验“前 N 张 viewport”；N 由命中率和成本决定。
7. **补充自动化保护**
   - 增加组件测试，确认默认策略为 `intent`。
   - 增加 loader/资源路由测试，确认核心响应不等待可选上游。

## 风险与取舍

- `intent` 会牺牲一部分“链接刚出现就已准备好”的导航速度，以换取更少浪费。
- 拆分后 UI 需要面板级骨架，否则用户可能感到内容闪现。
- 过晚触发可选面板可能使其体感变慢；过早触发又会重新引入浪费。
- 浏览器和 React Router 版本对预取触发、取消、去重的细节可能不同，不能只靠静态推断。
- 若上游有严格限流，实验阶段也应控制并发，避免测量本身制造异常流量。

## 验证方法

### 静态验证

- 检查所有 `AnimeCard` 调用点都显式或默认使用预期策略。
- 检查详情核心类型不再强制包含三个可选面板结果。
- 检查可选请求收到 loader/fetcher 的取消信号，并有独立错误边界。

### 运行时验证

- Chrome DevTools：在禁用缓存和保留日志两种模式下记录请求瀑布。
- 网络节流：Fast 3G/Slow 4G 下测量点击到详情主体可见时间。
- 服务端日志：按导航 ID 统计一个列表会话触发的详情和上游请求数。
- 对照场景：不滚动、不点击；滚动不点击；hover 不点击；hover 后点击；键盘 focus 后回车；触摸点击。
- 至少重复多次并报告中位数和 P95，不以单次本地结果下结论。

## 验收标准

- 普通列表仅滚动、不表达意图时，不再因卡片进入视口而批量请求详情数据。
- hover/focus 后点击仍可正确导航，且预取请求可被复用。
- 详情主体不等待 Bilibili、Comicat 或日志面板完成。
- 可选面板任一失败时，主体仍可用并显示明确的局部状态。
- 与基线相比，上游请求数和传输量有可复现下降；具体百分比在基线测量后设定，不预先虚构。
- 无搜索参数丢失、返回列表错误或键盘导航回归。

## 依赖 / 前置关系

- 与 `002-detail-request-waterfall.md` 强相关：详情可选请求并行化或拆分决定单次预取成本。
- 依赖 `003-bangumi-timeout-and-cancellation.md` 的取消信号传播，避免失效预取继续占用资源。
- 受 `005-cache-bounds-and-single-flight.md` 影响：single-flight 能减少同一详情的并发重复请求，但不能替代收紧预取策略。

## 学习要点

- 预取不是免费的；应同时评估命中率、单次成本和放大系数。
- `viewport` 适合低成本、高点击概率资源，不适合默认绑定昂贵聚合 loader。
- 并行化改善等待时间，但不会自动减少请求数量。
- 将首屏必需数据与增强型数据拆开，通常比单纯调节预取时机更稳健。
- 性能结论应把静态可确认的控制流与真实网络中的触发数量、缓存命中和尾延迟分开。
