## 实施记录（2026-08-20）

已落地推荐方案 B 的核心路径（日视图 `useCardExtra`）：

1. **共享 Observer**：`app/lib/shared-in-view.ts` 单实例 `IntersectionObserver`，`rootMargin: 200px`。
2. **客户端批处理**：`app/lib/card-extra-client.ts` 40ms 窗口合并 id，请求 `/api/anime/cards?ids=`；失败回退单卡 API。
3. **批量同源 API**：`routes/api/anime.cards.ts` + `fetchCardExtrasBatch`；去重、最多 20 id；上游并发上限 4；复用原有 `fetchCardExtra` 缓存；返回 `dataById` / `errorsById`。
4. 保留 `/api/anime/card/:id`。原始 subject 与详情共享缓存未做（可后续加）。

## 问题摘要

日历日视图会为选中日期的每个 `ScheduleCard` 调用 `useCardExtra(item.id)`。每个 Hook 创建自己的 `IntersectionObserver`，元素进入含 200px 预取区后分别请求 `/api/anime/card/:id`。同一 ID 已有浏览器内存缓存和在途去重，但不同 ID 仍是一卡一请求；可见卡片多时会形成 N 个客户端请求和最多 N 个上游条目详情获取。

这不是“页面初始化一定请求整周所有条目”：日视图只 map 当前日期，Observer 也延迟到临近可视区；周总览走另一个组件。准确的 N 取决于当前日期卡片数、视口和滚动。优化应保留按需特性，同时通过共享 Observer、批量端点、并发限制和原始 subject 缓存复用降低请求风暴。

## 当前证据

### 已静态确认

1. `start/app/components/anime-schedule.tsx:173-190` 的每个 `ScheduleCard` 都调用 `useCardExtra<HTMLDivElement>(item.id)`。
2. `start/app/components/anime-schedule.tsx:514-525` 对选中日期的所有 `selectedDay.items` 映射 `ScheduleCard`。
3. `start/app/components/anime-card-extra.tsx:36-57` 的 `useInViewOnce` 每次调用都创建新的 `IntersectionObserver`，使用默认 `rootMargin="200px"`，命中后断开。
4. `start/app/components/anime-card-extra.tsx:63-82` 每个 Hook 在进入可视区后调用 `loadCardExtra(id)`。
5. `start/app/components/anime-card-extra.tsx:6-33` 已有按 ID 的客户端 `Map` 缓存和在途 Promise 去重，但 `loadCardExtra` 仍为每个不同 ID 发起 `/api/anime/card/${id}`。
6. `start/app/routes.ts:5-8` 只注册单条目卡片端点 `/api/anime/card/:id`，没有批量卡片端点。
7. `start/app/routes/api/anime.card.$id.ts:4-9` 将每个请求直接交给 `fetchCardExtra(id)`。
8. `start/app/lib/bangumi/server/card-extra.server.ts:38-60` 在服务端按 card ID 缓存转换后的 `CardExtra`，未命中时调用 Bangumi `/v0/subjects/{id}`。
9. `start/app/lib/cache.ts:10-17` 表明该服务端缓存是进程内 `Map`，不能静态视为跨实例共享。
10. `start/app/lib/bangumi/server/detail.server.ts:7-13` 的详情路径有 `DetailPayload` 缓存，但原始 `fetchSubjectDetail` 仍直接请求同一个 subject detail URL；卡片增强与详情没有共享原始 subject 缓存。

### 需要运行时验证

- 一次日历访问实际产生多少 card API 请求、峰值并发、重复率和总字节。
- 浏览器和 Cloudflare 的 HTTP/2/HTTP/3 多路复用能缓解多少连接成本。
- Bangumi 上游延迟、限流阈值和错误率；不能仅凭 N+1 结构断言已经触发限流。
- 单个共享 Observer 相比多个 Observer 的主线程收益；网络优化可能比 Observer 数量更重要。
- 批量端点的合理批大小、等待窗口及用户滚动时的可感知延迟。
- 周总览组件是否存在独立增强请求路径，实施前需单独审计，避免只修日视图。

## 工作原理 / 为什么会慢

N+1 在这里指：先取得一份日历列表数据，再为 N 张卡片分别补取详情。即使浏览器可以多路复用，N 个 HTTP 请求仍有请求头、路由执行、鉴权/日志、序列化和缓存查询开销。服务端缓存未命中时，又会产生 N 次外部 subject detail 调用。

当前客户端缓存能避免同一 ID 在切换星期或重渲染时重复请求，这是有价值的，不应删除。但它无法合并“不同 ID 的同时首次请求”。每卡一个 Observer 也会增加对象和 effect 数量，虽然是否构成实际瓶颈需 Profile 验证。

批量请求可以把多个客户端往返合为一次，但如果服务端只是无限并发转发所有 ID，会把压力从浏览器搬到服务端。因此批量端点必须有 ID 上限、去重、并发限制、部分失败结果和缓存。共享原始 subject 缓存则可让卡片增强与详情页面复用同一次上游数据，避免两个不同派生缓存重复打 `/v0/subjects/{id}`。

## 影响

- **网络**：可视卡片同时进入 200px 区域时可能形成请求突发。
- **上游稳定性**：冷缓存下不同 ID 各触发上游请求，增加限流风险。
- **服务端成本**：大量小请求重复执行路由、解析和日志流程。
- **客户端开销**：每卡创建 Observer/effect；具体主线程影响待测。
- **用户体验**：增强字段可能以不一致速度逐卡出现，滚动时有内容跳变风险。

## 优化目标

1. 保留“仅临近可视区才加载增强数据”的按需行为。
2. 将同一可视批次的多个 ID 合并，显著降低客户端 HTTP 请求数量。
3. 使用共享 Observer 或集中可视区注册机制，减少每卡观察器实例。
4. 在客户端和服务端设置明确并发上限与批大小，避免请求风暴。
5. 抽取按 subject ID 的原始数据缓存，让卡片增强和详情路径共享。
6. 支持部分成功和单卡降级，不因一个 ID 失败丢弃整批结果。

## 非目标

- 不一次性预取整周所有番剧详情。
- 不改变日历基础接口、卡片排序或展示字段。
- 不在当前计划阶段新增批量路由或修改 Hook。
- 不假设 Bangumi 提供原生批量 subject API；若没有，服务端仍需受控并发聚合。
- 不为了消除请求数而把所有增强数据塞进首个 SSR 响应，导致 TTFB 和负载无界增长。

## 方案比较

| 方案                                                 | 做法                                                                             | 优点                                             | 缺点 / 风险                                                          |
| ---------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------- |
| A. 保留单 ID API，增加共享 Observer + 客户端并发队列 | 多卡共享一个 Observer，请求仍逐 ID，但限制同时请求数                             | 改动较小；保留细粒度缓存和失败隔离               | HTTP 请求数仍是 N；总开销和路由压力改善有限                          |
| B. 可视区批量 API + 共享 Observer                    | 短窗口收集临近可视 ID，调用 `/api/anime/cards?ids=...`；服务端去重、缓存、限并发 | 同时减少 Observer 和客户端往返；适合当前按需模式 | 批处理增加等待窗口和协议复杂度；部分失败、上限、安全需设计           |
| C. 在日历 loader 中服务端预聚合增强数据              | 初始日历响应包含当前日所有 CardExtra                                             | 客户端无二次请求，SSR 内容完整                   | 冷 miss 会把 N 个上游请求加入关键路径；可能过取未查看卡片，放大 TTFB |

## 推荐方案

推荐 **方案 B**，并分两层实施：

- 客户端建立共享 Observer 注册表和批处理队列。进入预取区的 ID 在很短的窗口内去重成批；已有缓存或在途项直接跳过。
- 服务端增加有上限的批量端点，每批只接受有限、去重后的数字 ID；从共享原始 subject 缓存读取，未命中项以受控并发请求上游，返回 `{ dataById, errorsById }`。

同时保留单 ID 端点作为详情交互、回退和渐进迁移路径。若运行时数据表明每页通常只有 1–3 个请求且没有尾延迟/限流问题，可先只实施方案 A；优化复杂度必须由测量支持。

原始 subject 缓存应位于数据层，而不是只缓存 `CardExtra`。`fetchCardExtra` 从原始 subject 派生字段；`fetchSubjectDetail` 也读取同一原始缓存。详情页自己的 persons/episodes 聚合缓存仍可独立存在。

## 分步骤实施计划（当前不要实施代码）

1. **测量当前行为**
   - 记录日视图初始、滚动和切换星期时 card API 请求数、峰值并发、缓存命中和响应时间。
   - 在服务端区分 card 派生缓存命中与 Bangumi subject 上游调用。
   - 用 React Profiler/Performance 检查多 Observer 是否有可见主线程成本。
2. **审计所有消费路径**
   - 确认日视图、周总览和其他组件是否都需要 CardExtra。
   - 记录每种视图一次合理的最大 ID 数，作为批量上限依据。
3. **设计原始 subject 缓存**
   - 定义 `getSubjectRaw(id)` 一类单一入口，包含 TTL、在途去重和可选跨实例缓存。
   - 让 card 派生和详情 subject 复用该入口；避免缓存类型被某一 UI 绑死。
   - 评估原始响应大小、隐私/许可、序列化成本和 TTL。
4. **设计批量 API 合约**
   - 只接受数字 ID，去重并限制数量、URL 长度；数量较大时考虑 POST JSON，但要权衡缓存性。
   - 返回按 ID 索引的数据和逐项错误，批次不因单项失败整体 500。
   - 设置服务端上游并发上限、单项超时和总请求预算。
5. **设计共享 Observer**
   - 由上下文/模块服务维护一个 Observer，并支持元素注册/注销。
   - 明确实际滚动根容器；当前卡片位于内部 `overflow-y-auto` 容器，实施时需验证默认 viewport root 是否符合预取预期。
   - 命中后注销元素，保持“一次触发”语义。
6. **设计客户端批处理器**
   - 收集短时间窗口内的 ID，过滤 `clientCache` 和 `inFlight`。
   - 控制批大小与同时批次数；快速滚动时使用背压而非无限排队。
   - 将批量响应分发给各卡片订阅者，组件卸载时不更新状态。
7. **渐进迁移**
   - 保留单 ID `loadCardExtra` 作为回退。
   - 先让日视图使用批处理，确认稳定后再评估周总览或其他路径。
   - 不同时重写卡片 UI，减少回归面。
8. **上线观测**
   - 监控每页批次数、每批 ID 数、上游并发、命中率、部分失败率和增强内容出现时间。
   - 与基线比较，而不是只看“端点数量变少”。

## 风险与取舍

- 批处理窗口过长会让首批可见卡片更晚显示；过短则合并效果差。
- 批量 GET 的查询字符串有长度限制；批量 POST 又较难利用通用 HTTP 缓存。
- 单批一个慢 ID 不应阻塞所有结果过久，需要逐项超时或分段返回策略。
- 共享原始缓存可能占用更多内存；跨实例存储还会引入序列化和一致性成本。
- Observer 的 `root` 若配置错误，会导致过早、过晚或永不触发。
- 并发限制会降低上游压力，但可能延后长列表后部数据，这是有意的稳定性取舍。
- 部分失败协议比单请求复杂，调用方必须正确区分未加载、失败和空数据。

## 验证方法

- 浏览器 Network 统计初始、滚动和切换日期时 `/api/anime/card*` 请求数及并发。
- API 集成测试覆盖 ID 去重、非法 ID、超上限、部分失败、超时和缓存命中。
- 故障注入一个慢/失败 ID，确认同批其他卡片仍能显示。
- 并发测试确认服务端不会超过设定的 Bangumi 上游并发数。
- 测试 card 后打开同 ID 详情，以及详情后返回 card，确认共享原始缓存减少重复 subject 请求。
- React Profiler 对比 Observer/effect 数量和滚动主线程开销。
- 在内部滚动容器、窗口缩放、快速滚动和组件卸载场景测试注册清理。

## 验收标准

- 同一批进入预取区的多张卡片不再各自产生一个客户端 HTTP 请求；请求数按批次而非按卡数增长。
- 页面只有共享的少量 Observer 实例，不再每个 `ScheduleCard` 创建一个实例。
- 批量端点有 ID 格式校验、去重、批大小上限、上游并发上限和部分失败响应。
- 同一 subject 的卡片增强与详情获取可共享原始 subject 缓存/在途请求，并有日志或测试证明。
- 单项失败不影响其他卡片和页面主体；现有静默降级体验不退化。
- 对比报告包含请求数、峰值并发、上游调用数、增强数据可见时间和错误率；实际收益与基线一致。
- 未预取整周数据，按需加载语义保持。

## 学习要点

- N+1 不只发生在数据库，也会发生在浏览器到同源 API、同源 API 到第三方 API 的两级链路。
- 同 ID 去重只能解决重复请求，不能解决多个不同 ID 的请求风暴。
- 批量端点如果没有并发限制，只是把 N+1 从客户端隐藏到服务端。
- 共享 Observer 是对象/回调优化，批量 API 是网络优化，两者应分别测量。
- 缓存原始领域数据比缓存单一 UI 派生结果更容易跨功能复用。
- 按需加载、批处理和背压可以同时存在，不必在“全预取”与“逐卡请求”之间二选一。
